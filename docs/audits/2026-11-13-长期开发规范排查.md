# KikuSub 长期开发规范排查报告（2026-11-13）

> 排查对象：`repo/`（`app/macos` 分支，HEAD `a457b7e`，50 个提交、2 个发版标签）。
> 判据：《如何用 AI 长期开发一个复杂项目》（Oil，视频 + Oil Book 第 07 章）第三～七章与第八章清单。

## 0. 一句话结论

**基建（护栏的"硬件"）已经做到很高水平，缺的是"闭环"（护栏的"软件"）：文档没有巡检、发版没有闸门、分支没有纪律、测试没有端到端。**

对照笔记第八章的 17 条清单，本仓库：

- **已扎实落地 7 条**（核心计算拆离、CLI 检查入口、静默截图、规则→测试升级、令牌体系、启动安全模式、版本号单一来源）；
- **部分落地 6 条**（方案四件事、递进分层、组件复用、机械化测试清理、任务派发纪律、规划拆分）；
- **未落地 4 条**（文档巡检、发版四步 + 程序化硬约束、分支/工作树纪律、端到端测试）；
- **不适用 3 条**（开源协议二开、更新配置秒级回滚、多模型交叉评估/双模型置信度——最后一条按你的要求不计分）。

换言之：**这个仓库已经"抗住"了大部分混乱，但抗不住"时间"**——过期文档、分支腐化、发版靠人记，这三件事恰恰是几个月后才会咬人的。

## 3. 值得保护的部分（后续"优化"不要拆掉）

1. **`AGENTS.md` 是索引不是全文**（12.7KB）。这是全仓最关键的一条架构决策：65KB → 12.7KB，让每次会话的启动成本可忽略。任何"把细节加回 AGENTS.md"的改动都是倒退。
2. **规则→测试的三级升级**（红线 → 契约 → 测试）已形成惯例，且真有 4 个守卫测试在跑。这是"AI 会忘、测试不会忘"的唯一可靠形式。
3. **`tools/shots/capture_matrix.sh` + PSNR 基线**。"编译通过 ≠ 没改坏"这条在别的项目通常只写进文档，这里真的能跑。
4. **`launchguard.cjs` 是纯函数 + 不碰 fs/弹窗**。安全模式本身绝不崩——分层做得比笔记里说的还干净。
5. **提交粒度**：50 个提交全是 Conventional Commits，按 `core,server` / `desktop` / `docs` 分层。这是 AI 长期开发里最容易烂掉、这里却没烂的东西。

## 4. P0：会直接咬人的四处

### D1. 过期文档仍在「现行文档」第一位 —— 最严重

- **现状**：`docs/AI优化与翻译-开发文档-2026-11.md` 共 1087 行，第 7 行写着
  `> 状态：待执行。`，但 M1–M4 早已全部 ✅；`docs/README.md:10` 把它列为**第一条现行文档**
  （「改 AI 提案之前必读」）。
- **已发生的错误引用**（这是"错文档比没文档更可怕"的教科书案例）：
  - `:305` 说 `server/app.py:170-177` 是 `include_router` 块 → 实际在 **`server/app.py:198-211`**；
  - `:728` 让人跑 `node --check static/reviewer.js static/qa_panel.js` → **`static/` 目录已不存在**。
- **双信息源**：同一件事有两份文档——`docs/README.md` 指向 1087 行大文档，`AGENTS.md` §3 契约索引
  指向 117 行的 `docs/contracts/ai-proposal.md`。新会话按 `AGENTS.md` 走会漏掉大文档里的验收标准；
  按 `docs/README.md` 走会读到已删界面的指令。**两条入口都不安全。**
- **代价**：AI 采信旧文档 → 改动落在错误位置（这正是笔记里"人很难发现"的那类暗坑）。
- **建议**：大文档降级为 `docs/archive/`（首行标注「禁止照它改代码」），现行契约只留
  `docs/contracts/ai-proposal.md`；如认为验收标准有价值，先**按当前代码校订**再并入契约。
  同时把 `docs/README.md` 的"现行文档"表与 `AGENTS.md` §3 做成同一份来源。

### T1. 没有端到端测试 —— 且文档已失真

- **现状**：`tests/` 38 个文件全是单元/集成（`TestClient` + 替身 runner，如
  `tests/test_server_jobs.py` 的 `_SlowRunner`）。**没有一条**覆盖「导入媒体 → 起任务 → 拿到 cue →
  改一条 → 导出 SRT → 校验文件内容」的闭环。
- **文档已失真**：`docs/contracts/engineering-practice.md:17` 声称保留「基础可用性 + 复杂易错路径的
  端到端」，`:27` 又写「保留两类…端到端」——**事实是不存在任何 e2e 用例**。
- **代价**：各层单独绿、拼起来断（接口字段改名、会话写回顺序、导出目录解析）只能靠人肉点，正是
  笔记 §4 说的"最兜底的那层业务连通性"没有兜住。
- **建议**：加 2–3 条**轻量** e2e（不加载模型）：用替身引擎跑 `POST /api/jobs` → 轮询 →
  `GET /api/cues` → `PATCH` 一条 → `POST /api/cues/export` → 断言文件内容。放在 `tests/test_e2e_flow.py`，
  用 marker 归为 `slow`，默认跑但可 `-m "not slow"` 跳过。

### R1. 发版没有闸门，只有三句话

- **现状**：`AGENTS.md` §6「发版」总共 3 行（:`120-124`），要求人「确认」version 与 tag 一致、
  图标未漂移、app 能起。**没有任何程序化检查**，`.git/hooks/` 为空。
- **已有测试只覆盖一半**：`tests/test_pack_version.py` 管住了
  `package.json` ↔ `package-lock.json` ↔ `build_app.sh`，但**不校验 Git 标签**；
  `docs/app-icon.png` 是否漂移、`build/pack/KikuSub.app` 是否是旧 sidecar，全靠人记。
- **没有的东西**：发版规范文档（四步：合入审查 → 本地实测 → 云端打包 → 发布日志）、
  CHANGELOG 或 Release notes 模板、`v*` 标签触发的一致性 CI job。
- **建议**：`docs/release.md`（四步 + 每步的检查命令 + 回滚口径）；CI 加一个 tag job（
  `tag == package.json.version`，否则红）；`tools/pack/build_app.sh` 已有的「sidecar 比源码旧就退出」
  是正确范式，把「图标漂移」「tag 不一致」也做成同类硬失败。

### B1. 分支腐化：`main` 落后 11 个提交

> **2026-11-13 已处理**：确认 `main` 为主线、`app/macos` 为开发分支；`main` 已快进到
> `app/macos`（`cd772d5`，本地）。分支模型写进 `AGENTS.md` §5 与 `CONTRIBUTING.md`，
> CI 现在会在 tag 不在 `main` 上时变红。**`origin/main` 仍需一次 push**（本地与远端尚未同步）。

- **现状**：`app/macos` 领先 `main` **11 个提交**（`main` 停在 `4a81c7e` = v0.2.0）；
  `git worktree list` 只有 1 个工作树；无分支命名/合入/删除策略。
- **代价**：GitHub 默认分支大概率是 `main` → 外部 clone / PR 默认落在**两个月前的旧代码**上；
  回滚基准、CI 覆盖范围、README 声称的版本三者不一致。笔记 §3.4 的 worktree 并行也没有落地条件。

  ② 明确 `app/macos` 是主线、在 GitHub 上把默认分支改过去、把 `main` 归档为 `archive/gradio-era`。

## 5. P1：结构性缺口

### P1-1. 前端零静态检查（`tsconfig strict` 是死配置）

`desktop/tsconfig.json` 开了 `strict: true`，但 `package.json` 的 scripts 里**没有任何 `tsc`/`svelte-check`**，
`vite build` 只转译不类型检查；也没有 eslint / prettier / svelte.config。
前端目前只有两个手写守卫（`svelte-imports.test.cjs`、`style-drift.test.cjs`）在兜。
**建议**：加 `svelte-check --fail-on-warnings`（或至少 `tsc --noEmit`）作为 `npm run check`，
并进 CI。这是"AI 写错一个不存在的导出名"的最便宜防线。

### P1-2. CI 只覆盖 Python，不覆盖桌面端

`.github/workflows/ci.yml` 两个 job（`lint` / `test`）全是 Python；**`npm ci` / `npm run build` /
`npm run test:main` 都不在 CI**。也就是说桌面层（主进程 1570 行 + 渲染层）在 CI 里完全不可见。
**建议**：加第三个 job（`ubuntu` 上 `npm ci && npm run build && npm run test:main`），成本不到 2 分钟。

### P1-3. 环境未钉版本（已经分叉了）

无 `.python-version` / `pyproject.toml` / `engines` / `.nvmrc`。实测：本机 `python3 -V` = **3.14.8**，
CI = **3.12**（lint job 还跑 3.10/3.11），`server/__pycache__` 里已有 `cpython-314` 产物
——说明确实用 3.14 跑过。Node 本机 v26.11.1，CI 不测 Node。
**建议**：`.python-version`（3.12）+ `package.json engines`，CI 与本地对齐；可选 `uv lock`/`pip-compile`
做依赖锁定（现在 `requirements.txt` 只有下界）。

### P1-4. 测试分层只有"顺序"，没有"时机"与开关

`AGENTS.md` §5 给了一条串行验证链（pytest → smoke → build → test:main → 截图），但没有：

- pytest marker（`fast` / `slow` / `needs_ffmpeg` / `needs_macos`），无法 `-m "not slow"` 秒级回环；
- 重型项（`tools/pack/rebuild.sh`、`capture_matrix.sh`、`score_srt.py`、`build_dmg.sh`）的**触发时机表**
  ——现在只有截图这一项写了"改了界面再跑"。

实测全量 pytest 只要 48.7s、node 只要 98ms，所以**这不是性能问题，是纪律问题**：没有明确写"改文档不必跑 pytest、
改 core 只跑 tests/test_core*"这类边界，AI 会保守地全跑或乐观地全不跑。
**建议**：AGENTS §5 换成一张「改动范围 → 必跑项 → 可选/收尾项」的矩阵；给 `needs_*` 用例加 marker。

### P1-5. 没有文档巡检机制（笔记 §5.5 的核心）

目前防过期文档的手段只有两条：`docs/README.md` 把旧文归到「历史记录（存档，不再更新）」的手写表格，
以及归档件首行加「禁止照它改代码」。**没有自动检查**：

- 没有链接/路径有效性检查（本次人工跑了一遍，md 链接 0 失效——但这是运气不是机制）；
- 没有"契约里的数字/常量 vs 代码"的对账（`50 步` 出现在 `server/sessions.py:23`、`routes_cues.py:449`、
  `api.ts:891` 与多份契约里；`CLICK_SLOP=4` / `RULER_H=17` / `LANE_H=17` 只在 `ReviewView.svelte:95-100`）；
- 全仓已有 **13 处**「已过期 / 补记 / 不再适用」的维护性注释（`docs/sprints/2026-11-ui/交接-2026-11-12.md`
  靠顶部「2026-11-13 补记」续命，`docs/sprints/2026-11-ui/README.md` 表格里直接写「首部的状态说明已过期」）。

**建议**：`tests/test_docs_health.py` 三件事——① 所有 md 相对链接存在；② 反引号里的 `path` 形式引用存在；
③ `docs/` 下带 `> 状态：` 头部的文档，状态词只能是 `现行/待执行/已完成/已归档` 且「已完成」不得出现在
「现行文档」表里。再加一条 `tools/audit/docs_drift.py` 做"契约声明常量 ↔ 代码常量"的对账（可选）。

### P1-6. 单模型下的 Review 替代物不存在

按要求不计多模型分，但**替代物必须补**：笔记的 Review 四件事（跑通/优雅/测试意义/复用基建）现在只以
codex 提示词形式存在（`engineering-practice.md:57-62`），单模型下没有可执行动作。
**建议**：`docs/review.md` —— 合入前逐条打勾的 6 问（含"有没有复用手写轮子""有没有加没人跑的测试"
"有没有新增裸 px / 裸色值""文档是否需要同步"），并要求在 PR 描述里贴勾选结果（配合 PR 模板）。
配一个固定动作：`git diff` 生成后**隔一轮再自读**，专找"只有作者才看得懂"的实现。

### P1-7. 没有待办单一入口 / 没有方案模板
