## 2. 冻结决定（改这些先改文档）

### D-1 时间戳由**结构**保证，不靠提示词

模型**永远看不到、也不返回时间戳**。它只收发 `{i, text}`；软件用原始 cue 的时间码 join 回去。

```python
after = {item["i"]: item["text"] for item in result["items"]}
cues = [SubtitleCue(start=c.start, end=c.end, text=after[i + 1])
        for i, c in enumerate(source)]
```

**任何实现都不得把 `start`/`end` 放进送给模型的载荷里。** 这不是风格问题：它是 A1 唯一可靠的保证。

### D-2 一个提案层，两个生成入口

- 提案文件是**唯一**的 AI 产物格式（§3.1）。
- `in-app`：sidecar 调模型 → 写提案 → 前端渲染。
- `skill`：外部 agent 自己写提案 → 前端渲染。
- 前端**不关心**提案是谁生成的。

### D-3 译文存平行轨，不塞进 `cue.text`

`review_cues` 的 `text` 永远是源语言。译文单独存 `translations[lang]`，与 `review_cues` 逐条对齐。

### D-4 双语 = 一条 cue 两行

导出双语时生成 `SubtitleCue(start, end, "原文\n译文")`。不用"同区间两条 cue"，因为播放器兼容性最好，且重新导入时 `srt_to_cues()` 会原样解析成一条带 `\n` 的 cue。

### D-5 应用 = 整批一次 undo

27 处改动也只在 `_push_history()` 里压一次。**禁止**逐条压栈。

### D-6 模型输出永远"列满本块全部条目"

不做"只返回改动项"。理由：校验规则统一（条数必须相等）、diff 能显示"AI 没动的条"、不需要 `kind` 分支去猜缺省值。

## 3. 数据契约

### 3.1 提案文件 `proposal.json`

```json
{
  "version": 1,
  "kind": "polish",
  "src_lang": "ja",
  "dst_lang": "zh-Hans",
  "source": {
    "path": "/Users/x/…/xxx.srt",
    "count": 312,
    "digest": "9f2c…"
  },
  "model": "deepseek-flash",
  "entry": "in-app",
  "created_at": 1762800000.0,
  "chunks": 2,
  "glossary": [{ "src": "千尋", "dst": "千寻" }],
  "items": [
    { "i": 12, "before": "君の名前は？", "after": "君の名前は?", "note": "标点" }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `version` | ✅ | 固定 `1`；读到其他值 → 拒绝（不猜） |
| `kind` | ✅ | `polish` \| `translate` |
| `src_lang` | ✅ | `ja` 等 |
| `dst_lang` | translate 必填 | `zh-Hans` / `zh-Hant` / `en` / `ko` …；polish 时省略 |
| `source.count` | ✅ | 生成时的 cue 条数 |
| `source.digest` | ✅ | 见 §3.2 |
| `entry` | ✅ | `in-app` \| `skill`，仅用于 UI 标注来源 |
| `chunks` | ❌ | 分块数，统计用 |
| `glossary` | ❌ | translate 的术语表，最多 80 条 |
| `items` | ✅ | **必须列满 `source.count` 条**，`i` 从 1 连续到 n |
| `note` | ✅ | 该条改动的 4 字理由；未改动填 `""`。**polish 中 `after != before` 时不得为空** |

`before` 是给人和 agent 自检看的；**服务端应用时以自己的 `review_cues` 为准**，不用提案里的 `before`。

### 3.2 源指纹 `digest` 算法（写死在契约里，agent 必须能复现）

```python
lines = [f"{idx}\t{text.strip()}" for idx, text in enumerate(texts, start=1)]
digest = hashlib.sha256("\n".join(lines).encode("utf-8")).hexdigest()
```

- `texts` = 按顺序的**源语言**字幕文本（`review_cues[i].text`）
- **去行尾空白，保留行内空白**（`str.strip()`）
- 换行分隔，**末尾不加换行**
- `idx` 从 **1** 开始，十进制无补零

软件侧唯一实现：`core/ai_proposal.py: source_digest(texts) -> str`。skill 文档里附同一段算法。

### 3.3 文件命名与目录

| 产物 | 路径 |
|---|---|
| 润色提案 | `{output_dir}/{stem}.ai-polish.json` |
| 翻译提案 | `{output_dir}/{stem}.{dst_lang}.ai-translate.json` |
| 译文工作稿（暂存用） | `{output_dir}/{stem}.autosave_draft.i18n.json` |
| 导出：原文 | `{export_dir}/{stem}.srt`（现状不变） |
| 导出：译文 | `{export_dir}/{stem}.{dst_lang}.srt` |
| 导出：双语 | `{export_dir}/{stem}.bilingual.srt` |

`stem` 与现有导出完全一致（`routes_cues._media_stem()`），不另立规则。

## 4. M1｜提案层 + AI 优化台

### 4.1 目标

不接任何模型，也能走完整流程：**手工放一份合法提案 → 双栏展示 → 双击改 → 采纳 → 应用 → ⌘Z 退回**。

### 4.2 后端

#### 4.2.1 新增 `core/ai_proposal.py`（无 UI / 无网络依赖）

```python
PROPOSAL_VERSION = 1
KINDS = {"polish", "translate"}

def source_digest(texts: list[str]) -> str: ...
def build_proposal(kind, src_lang, dst_lang, texts, model, entry, items, **extra) -> dict: ...
def validate_proposal(data: dict, texts: list[str]) -> ProposalCheck: ...
def proposal_path(output_dir: Path, stem: str, kind: str, lang: str = "") -> Path: ...
def apply_polish(source: list[SubtitleCue], items: list[dict],
                 accept: set[int], edits: dict[int, str]) -> list[SubtitleCue]: ...
```

`validate_proposal` 逐条检查并返回 `ProposalCheck(ok, errors, warnings, digest_match)`：

| 检查 | 失败后果 |
|---|---|
| `version == 1` | 拒绝 |
| `kind in KINDS` | 拒绝 |
| `len(items) == source.count` | 拒绝 |
| `{i} == {1..n}`（无缺、无重、无越界） | 拒绝 |
| `source.digest == source_digest(texts)` | **拒绝（409）** |
| polish：`after != before` 但 `note == ""` | 警告（不拦） |
| polish：改动率 > 40% | 警告（前端弹二次确认） |
| 任一条 `after` 为空 | 该条退回 `before`，计入 `warnings` |
| 任一条长度 > 源长度 × 3 | 同上 |

`apply_polish` 只做三件事：按 `accept` 挑条、按 `edits` 覆盖、**保留原 `start/end`**。不得重排、不得过滤空条（空条已在校验阶段处理）。

#### 4.2.2 应用入口 `POST /api/ai/apply`

```
body: { kind, accept: [12, 15, 27], edits: {15: "人工再改过的文本"} }
```

流程：

1. 读当前 `session.review_cues`；
2. 读提案文件（或 body 内联 `proposal`）；
3. `validate_proposal(...)` —— 不通过：`409`（digest）/ `422`（结构），**不动字幕**；
4. 构造新 cue 列表；
5. 若 `accept` 为空、或应用后无任何文本变化 → **不压历史**，直接返回 `changed: 0`；
   否则 `session._push_history()` **仅一次**；
6. 返回 `{cues, cue_count, can_undo, can_redo, changed: n}`。

翻译轨的应用走 `/api/translations`（M3），**不走这里**。

#### 4.2.3 导入外部提案 `POST /api/ai/proposal/import`

外部 agent 可以把提案写到任何地方。导入接口负责：读文件 → 解析 → 按 §4.2.1 全量校验 →
**通过后**才 `write_text_atomic()` 落到标准位置（`proposal_path()`）。校验不通过一律不落盘。

配套原生对话框 `dialog:pick-proposal`（`.json` 过滤），preload 暴露为
`window.kikusub.pickProposal()`。**不复用 `pickSubtitle`**：它只认 `.srt/.vtt`。

## 5. M2｜软件内润色

### 5.1 目标

设置里填 Base URL / 模型 / Key，点「生成提案」，得到一份和 M1 手工文件**完全同构**的提案。

### 5.2 密钥与配置

#### 5.2.1 存储

> **2026-11-11 修订（见 §11.4）**：原方案用 Electron `safeStorage`（系统钥匙串），
> 实测在「每次装配都重新 ad-hoc 签名」的工作流下会反复失效。现改为**本机主密钥加密**。

- 32 字节随机主密钥存 `{dataDir}/.ai-key`（0600），`preferences.json` 里存
  `aik1:` 前缀的 AES-256-GCM 密文。重建 / 重签名 / 换 Electron 版本都不影响。
- 旧版 `safeStorage` 密文（无前缀、内含 `v10`）会被识别为 legacy：能解开就自动迁移，
  解不开就标记 `broken`，界面提示"请重新填写一次"。**不会静默假装没配过。**
- 主进程新增 IPC：`secrets:set-ai-key` / `secrets:get-ai-key` / `secrets:clear-ai-key`（`desktop/main/main.cjs`），preload 暴露为 `window.kikusub.aiKey.set/get/clear`。
- 渲染进程**只在发起请求那一刻**取 key，放进 `X-AI-Key` 请求头。
- sidecar **不落盘、不进 `JobRecord`、不进 WS 快照**。
- `server/app.py` 的日志中间件对 `/api/ai/*` 只记方法/路径/状态/耗时；**任何情况下不打印请求头**。

> 密文与主密钥同机存放，防护级别低于系统钥匙串：它挡的是「preferences.json 被单独拷走/误传」，
> 不是「本机被攻破」。这条边界写进设置页文案，不要对用户过度承诺。

- 逐块结果拼成完整 `items`（按 `i` 排序）；

- 有块失败 → 整体标记 `partial`，**不落盘**，把失败块范围返回给前端（"第 3/5 块失败：超时"）。

### 5.4 任务化

`POST /api/ai/jobs`：

## 6. M3｜翻译

### 6.1 数据模型（`server/sessions.py`）

```python
@dataclass
class TranslationTrack:
    lang: str
    texts: list[str]          # 与 review_cues 等长
    base: list[str]           # 生成时的源文本快照，用于逐条过期判断
    created_at: float
    entry: str = "in-app"     # in-app | skill

@dataclass
class Session:
    # …现有…
    translations: dict[str, TranslationTrack] = field(default_factory=dict)
    translation_undo: dict[str, list[TranslationTrack]] = field(default_factory=dict)  # 每语种 20 步
```

**过期判定**（服务端算，前端只显示）：

```python
def stale_indices(track, cues) -> list[int]:
    return [i for i, c in enumerate(cues)
            if i >= len(track.texts) or track.base[i] != c.text]
```

**结构变更**（增删条）→ `base` 长度不匹配 → 所有越界条目自动进 `stale`。**不做整轨作废**：能救的条继续用，省得重翻全片。

### 6.2 翻译生成

#### 6.2.1 两遍走

**第一遍：术语表（仅当 `count > ai_translate_chunk_cues` 时执行）**

- 输入全片原文文本（不带 i），要求输出 `{"glossary":[{"src":"千尋","dst":"千寻"}]}`；
- 上限 80 条；失败不阻塞（降级为无术语表，记 `log.warning`）。

**第二遍：分块翻译**

| 参数 | translate |
|---|---|
| 每块条数 | `ai_translate_chunk_cues`（默认 120） |
| 上下文 | 前/后各 `ai_context_cues`（默认 5，与润色共用同一字段，可调到 10） |

system prompt（写死）：

```
你是日语影视字幕翻译。把给定的日语字幕逐条译成{目标语}。

要求：
- 一条原文对应一条译文，条数必须相同，i 必须与输入一致
- 译文要能在单行内显示：中文不超过 18 个全角字，超长时压缩措辞，绝不拆条
- 保留人物称呼与敬语层级；人名按术语表统一
- 不加解释、不加括号补充、不音译外来语原文
- 参考 context_before / context_after 理解语境，但只为 items 输出译文

只输出 JSON：{"items":[{"i":1,"text":"…","note":""}]}
```

#### 6.2.2 落盘与应用

- 提案：`{stem}.{dst_lang}.ai-translate.json`（`kind=translate`，`items` 列满全部）；
- `POST /api/translations` 应用：校验 `len(texts) == len(review_cues)` 且 digest 匹配 → 写 `translations[lang]`，压一次 `translation_undo[lang]`；
- 应用翻译**不改** `review_cues`，因此**不碰** `undo_stack`。

### 6.3 核对台显示

#### 6.3.1 开关位置

放 `components/Inspector.svelte` 顶部（标题下方、字幕轨道上方）一排：

```
[原文 | 译文 | 双语]   [中文 ▾]
```

理由：检查器已承载轨道与导出，语义同源；工具栏已过密。

- 译文选项卡仅在有对应轨时启用，否则置灰并提示"还没有译文"。
- 选择持久化到 `localStorage['kikusub.track']` 与 `['kikusub.trackLang']`。

#### 6.3.2 三态行为

| 态 | 表格 | 视频字幕叠加层 |
|---|---|---|
| 原文 | 现状 | 现状 |
| 译文 | 文本替换为译文，`stale` 条左侧黄点 | 显示译文 |
| 双语 | **每行两行文字**，原文上、译文下（字号 ×0.85） | 两行（复用 `rebuildCaptionIndex` 的 `(start,end)` 聚合） |

⚠️ **虚拟列表行高**：`ReviewView` 目前是固定行高。双语态改为**固定双行高**（`ROW_H × 2`），**不得**做自动测量行高——会与虚拟滚动打架。

#### 6.3.3 双语 cue 的构造（单一实现）

```python
def bilingual_cues(cues: list[SubtitleCue], track: TranslationTrack) -> list[SubtitleCue]:
    out = []
    for i, c in enumerate(cues):
        t = track.texts[i].strip() if i < len(track.texts) else ""
        out.append(SubtitleCue(c.start, c.end, f"{c.text.strip()}\n{t}" if t else c.text))
    return out
```

放 `core/i18n.py`，**导出与显示共用这一份**，禁止两处各写一遍。

### 6.4 导出

`POST /api/cues/export` body：

```json
{ "format": "SRT", "track": "both", "lang": "zh-Hans" }
```

| `track` | 源 | 说明 |
|---|---|---|
| `source` | `review_cues` | 默认值，行为与现在完全一致 |
| `target` | 译文轨转 cue | 文件名加 `.{lang}` |
| `both` | `bilingual_cues()` | 文件名加 `.bilingual` |

- `track != "source"` 且该语种无轨 → `409`；
- VTT 双语同样合法（`WEBVTT` 多行 cue 支持）；
- **TXT 双语不合并成一行**，按 `原文\n译文` 输出两行。

### 6.5 暂存

`POST /api/cues/draft` 额外写 `{stem}.autosave_draft.i18n.json`（所有轨的 `{lang, texts, base}`）。`restore` 一并恢复。否则重启后译文全丢。

| 422 | 结构校验失败（版本、条数、序号、kind） |
| 424 | 模型调用失败（`AiError`），body 带 `chunk` 与原因 |
| 429 | 上游限流（重试耗尽） |
| 503 | `safeStorage` 不可用 / AI 未启用 |

## 附录 C：术语

| 词 | 含义 |
|---|---|
| 提案 / proposal | AI 产出的纯文本映射 JSON，不含时间码 |
| 源指纹 / digest | 源文本列表的 sha256，防错位应用 |
| 平行轨 | 与 `review_cues` 逐条对齐的译文数组 |
| 润色 / polish | 只修识别错误，不翻译 |
| `stale` | 源文本已变、译文需重做的条目下标 |

### 11.4 AI 密钥存储：最终选型（2026-11-11）

**现象**：设置里填过的 API Key 重启后消失；再填新 Key 报「系统钥匙串不可用」。

**根因**：`safeStorage`（macOS Keychain）条目的 ACL 认的是**代码签名要求**。ad-hoc 签名
（`codesign --sign -`）的要求里带 cdhash，代码一变就变，于是重打包后读不回旧条目。

**评估过的三个方案**

| 方案 | 结论 | 理由 |
|---|---|---|
| A. `safeStorage` + ad-hoc | ❌ | 每次重打包 Key 就丢 |
| B. `safeStorage` + 自签名证书 | ❌（本项目不合适） | 只解决**开发机**；以 DMG 分发时，**每次发版 cdhash 都变，所有用户升级后 Key 全部失效**，而没有 Developer ID 就无从修复。且自签名证书默认不算"有效身份"，必须手动设「始终信任」 |
| C. **本机主密钥 + AES-256-GCM** | ✅ **采用** | 与签名身份、版本号、钥匙串状态全部无关；开源 + DMG 分发场景下唯一不会"升级即丢"的方案 |

**为什么 B 在"上架/公证"之外没有意义**：证书的价值是让签名要求脱离 cdhash。但自签名证书
在别人机器上会触发 Gatekeeper「无法验证开发者」，而且我们无法控制用户环境的钥匙串行为。
真正需要稳定签名要求时，正确做法是 **Apple Developer ID + 公证**——那时 `safeStorage`
在任何用户机器上原生可用，根本不需要本方案。

**实现**

| 项 | 做法 |
|---|---|
| 加密 | `desktop/main/aikey.cjs`：AES-256-GCM，纯 Node，可单测 |
| 主密钥 | `{dataDir}/.ai-key`，32 字节，0600，首次使用时生成 |
| 密文 | `preferences.json` 的 `aiKey`：`aik1:` + base64(iv\|tag\|body) |
| 旧数据 | 更早版本的 `v10` 钥匙串密文已无法解开 → `broken/legacy`，界面提示重填一次 |
| 签名 | `build_app.sh` 保持 ad-hoc（与密钥无关，不再警告） |
| 用例 | `desktop/test/aikey.test.cjs`（8 项：roundtrip / 换密钥 / 篡改 / 长度损坏 / 权限 600） |

**诚实的边界**：主密钥与密文同机存放，防护级别低于系统钥匙串。它挡的是「preferences.json
被单独拷走/误传」，不是「本机被攻破」。设置页文案按这个口径写，不做过度承诺。

### 11.5 手动粘贴通道（M3 补充，2026-11-11）

给没有 API Key、或想用网页版模型的用户开的一条路：**复制提示词 → 粘到任意聊天窗 →
把回复粘回来 → 同一套 diff**。

| 步骤 | 接口 / 实现 |
|---|---|
| 组提示词 | `GET /api/ai/prompt?kind=translate&lang=zh-Hans` → `core.ai_translate.build_manual_prompt()` |
| 复制 | 渲染层用 `window.kikusub.writeClipboard()`（主进程剪贴板） |
| 解析回复 | `POST /api/ai/from-srt` → `core.ai_translate.proposal_from_srt()` |
| 对照与应用 | 与自动生成完全一致：`AiView` 双栏 → `POST /api/translations` |

**为什么提示词里带时间戳，却仍然安全**

- 带时间戳是为了让模型逐条对齐（长片不带序号极易错位）；
- 解析回来时**只按顺序取文本**，序号与时间戳**全部丢弃**，时间轴一律用本项目 cue 的
  `start/end` 重建——D-1 没有被破坏，模型改坏时间轴也污染不了交付文件；
- 条数必须与当前字幕一致，否则**整批拒绝**（合并/拆句/漏翻都在这里被抓住）；
- 时间戳偏差 > 1s 的条目会出现在 `warnings` 里（提示可能整体错位），但不影响落库。

**提示词模板**（`MANUAL_PROMPT`）

```
请将以下 SRT 日语字幕翻译为{目标语}：
风格要求：综合全片先理解整部影片的风格，例如语气是温柔撒娇还是粗俗轻视，然后再结合上下文翻译。
格式要求：严格保留原 SRT 的序号和时间戳不变。
仅输出翻译后的{目标语}内容，不要解释、不要 markdown 代码块。
内容如下：
<subtitles>
{当前字幕的 SRT}
</subtitles>
```

**边界**：目前只对翻译开放（`kind=polish` 返回 422）。润色同样可以套这条路，
但提示词与"哪些条算改动"的判定需要单独设计，留给后续。
