# P2：双引擎顺序协同设计（2026-11-20）

> 目标：一次任务里顺序跑两个日语引擎——主引擎写主稿，副引擎写只读第二列，
> 再把副稿里「主稿没有、且可信」的补漏建议送进质检队列。
> 本文件是实施前的冻结设计；第一步 `core/ensemble.py` 已落地（见 §11）。

## 1. 目标与非目标

**目标**

- 一次点击完成「主稿 + 副稿」，不用先转一遍再手动跑第二遍；
- 两个引擎使用各自验证过的 VAD（Qwen → Silero 20s，Whisper → WhisperSeg）；
- 第二列保持只读，采纳补漏必须经过质检队列与统一 50 步历史；
- 低内存设备上顺序跑，两个引擎不常驻；内存不足时给出可操作提示，不静默 OOM。

**非目标**

- 不做逐句并行推理（单槽 + 统一内存，并行只会互相换页）；
- 不自动合并两稿文本；副稿只提供差异与建议；
- 不在 P2 做区间 dual（先整片，区间后续按需扩展）；
- 不引入新的引擎 key 白名单：主/副角色都从 `core.engines` 的语种与 `reviewable` 能力推导。

## 2. 现有约束（实现时必须遵守）

- `JobRegistry` 单槽：dual 仍是一个 job，两个 pass 在同一 worker 线程内顺序执行；
- `TranscribeRequest.alt_review` 已能把整片结果写进第二列，`_apply_alt_review`
  不覆盖核对台、不进 50 步历史；
- `DualView` 只读；任何写回都必须走 `session.replace_review(..., label=...)`；
- 质检队列由 `core/audit.build_audit_items` 生成，动作在 `core/qa.py`，
  HTTP 在 `server/routes_qa.py`；新增 kind 必须同时补三处与前端 `Kinda` 文案；
- 改 VAD / 断句口径必须用 `score_srt.py` 同区间验证（本设计不改切分算法）。

## 3. 角色与默认配对

用户创建 dual 任务时选主/副角色；默认值来自 P1 实测：

| 主引擎 | 默认副引擎 | 主 VAD | 副 VAD |
| --- | --- | --- | --- |
| Qwen3-ASR（主） | Anime Whisper | Silero 20s | WhisperSeg |
| Anime Whisper（主） | Qwen3-ASR | WhisperSeg | Silero 20s |

规则：

- 主/副必须同语种（当前只有日语引擎可配对；中文引擎不参与 dual）；
- 主/副不能是同一个引擎；
- 用户可以交换角色，但不允许把 Whisper 的 WhisperSeg 强加给 Qwen：
  `QwenCtcConfig.vad_backend` 固定 `silero`（P1 交叉核对 CER +1.14pt）；
- 默认配对只做「推荐」，前端仍允许用户改副引擎。

## 4. 一次 dual job 的流程

```
POST /api/jobs/transcribe { kind: "dual", engine: primary, secondary_engine: secondary, ... }
  -> JobManager.start_dual(primary_req, secondary_req, session, apply)
       任务前预检：物理总内存 / 空闲 TTS 卸载
       Pass A: run_transcription(primary_req)     进度 [1/2] 主引擎 0.02–0.47
       apply A -> session.review_cues（主稿）
       release_engine(primary) + gc.collect() + mps.empty_cache()  进度 0.48
       Pass B: run_transcription(secondary_req)   进度 [2/2] 副引擎 0.50–0.96
       _apply_alt_review(B)                      第二列只读
       build_ensemble_suggestions(A, B)          进度 0.97
       写 ensemble 质检项 + 任务报告
  -> job.result: { dual: true, primary, secondary, primary_cues, secondary_cues,
                   ensemble_count, secondary_error, alt_review }
```

约束：

- 默认只接整片；**区间/替换范围也允许**，但第二列必须只局部更新该范围
  （见 §6），不能把范围外已有的对照清空；
- 两个 pass 都写各自的引擎产物（`output_suffix` 已按引擎区分文件名）；
- Pass B 用 `write_audit=False`，避免覆盖 Pass A 的质检队列；ensemble 项在 B 之后
  由服务层合并进 A 的 payload；
- 两个 pass 必须共享同一份 `audio_cache` 16k WAV；开了 `separate_vocals` 时还要
  共享同一份人声分离 WAV（`ensure_vocals_wav` 的缓存键已包含媒体指纹与区间），
  绝不解码/分离两次；
- 取消令牌在两个 pass 之间检查；Pass B 期间取消只中止 B（见 §9）。

## 5. 内存安全闸门

单槽只保证「不同时跑」，不保证「前一个引擎已经让出内存」。但 **不能** 在 Pass A
跑完后仅凭 `available` 硬拦截：macOS 会把刚读过的大视频缓存在统一内存里，
`available` 偏低是正常的，等 A 跑完半小时再报错体验最差。策略改成：

**任务开始前（硬闸门）**

1. 读取物理总内存 `total_ram_gb`；
2. `total < 12GB`（即 8GB 机型）→ 直接拒绝 dual，提示「双引擎顺序协同需要 12GB
   以上内存；当前 XGB，请只跑主引擎」。16GB 机型放行；
3. 触发 `engine_idle` 卸载已加载的 OmniVoice TTS（`release_tts` / 现有回调），
   避免 TTS 与第一个 ASR 抢统一内存。

**Pass A 结束后（预释放，不做硬拦截）**

1. `pipeline.release_engine(primary)`（Whisper `release()` / Qwen `unload()`）；
2. `gc.collect()`；
3. `torch.mps.empty_cache()` / `torch.cuda.empty_cache()`（按设备）；
4. 只记录 `available_ram_gb` 到报告；不因这个瞬时值失败。若 Pass B 真的 OOM，
   由现有异常路径报「副引擎内存不足」，主稿仍保留。

实现位置：`core/memory.py` 提供 `total_ram_gb()` / `available_ram_gb()`
（macOS 用 `os.sysconf` / `vm_stat`，Linux 用 `/proc/meminfo`；不新增 psutil 依赖），
`server/jobs.py` 在任务开始前调用硬闸门，Pass A 后调用预释放。测试注入
`memory_probe` / `tts_releaser`，不真的吃内存。

## 6. 数据契约

`TranscribeJobRequest` 新增：

```python
kind: "transcribe" | "proxy" | "compare" | "dual"
secondary_engine: str = ""        # kind=dual 必填
```

`JobSnapshot.kind="dual"`，`result` 至少包含：

```json
{
  "dual": true,
  "primary_engine": "qwen",
  "secondary_engine": "whisper",
  "primary_cues": 92,
  "secondary_cues": 100,
  "ensemble_count": 7,
  "secondary_error": "",
  "alt_review": { ... 现有第二列摘要 ... }
}
```

会话侧：

- 主稿走现有 `_apply_cues(..., apply="replace")`；
- 副稿走现有 `_apply_alt_review`（只读、按媒体落盘）；区间/替换范围模式下
  `_apply_alt_review` 必须支持 `replace_range`：只替换该范围内的第二列条目，
  范围外原样保留；整片模式才整列覆盖；
- Pass B 的 `TranscribeRequest` 复用 Pass A 的 `audio_cache` 结果：同一媒体、
  同一区间、同一 `enable_loudnorm` / `separate_vocals` 下不重新解码或分离；
- ensemble 项追加到本次质检 payload 的 `items`，`kind="ensemble"`，按时间排序。

## 7. 补漏建议（`core/ensemble.py`，已落地）

- 对齐复用 `core.dual_review.build_review`，只取 `only_b` 行；
- **时间硬排重（防止重叠双字幕）**：候选与 Pass A 任意字幕的时间交集达到
  「候选时长的 20%」或「0.15s」→ 一律不作为补漏，留在 DualView 当断句差异；
- 过滤：实字 < 2、时长 < 0.35s、纯标点/省略号、纯发声碎片（「んー」「ぺろっ」「はむぅ」「んっ…んんっ」这类全假名拟声）；
- **局部相似去重**：只在候选句前后 ±5s 内找主稿相似度 ≥0.85 的句子，视为
  断句/边界差异；不得全片比对——长片里「はい」「すごい」相隔十几分钟重复很正常；
- 副稿自身同文去重也只在 ±5s 内；远距离重复是正常台词，保留；
- 上限 50 条，按时间排序；
- 每条带 `engine / reason="only_b" / nearest_a / duration`，质检里能直接试听与对照。

质检 kind `ensemble`：

- `AUDIT_KIND_META["ensemble"]`：名称「双引擎补漏」、组 `miss`、提示
  「副引擎听到了主稿没有的句子」；
- **与空白项合并升级**：ensemble 候选在时间上命中 Pass A 原本的 `missed`
  （切片内为空）或 `coverage`（未覆盖空白）时，直接移除那条空白项，用有台词的
  ensemble 项替代；避免同一处出现两张待核卡；
- 采纳 = 把该条插回核对台，走 `session.replace_review(..., label="采纳双引擎补漏")`，
  一步历史、⌘Z 可退；已存在同句时不重复插入；
- 删除 = 标记跳过，不改字幕；
- `_audit_coverage` 对 whisper/qwen 的 dual 结果返回 true；单引擎不生成该 kind。

## 8. UI

转写页「结果处理」增加第三个目的地：**双引擎顺序协同**（现有两个：核对台 /
双引擎复核）。选中后出现：

- 主引擎下拉（当前启用、日语）；
- 副引擎下拉（另一个日语引擎，默认按 §3 配对，可交换）；
- 一行内存预估：「顺序执行，峰值约 max(主, 副) + 1GB；副稿只读」；
- 开始按钮与现有转写共用，`altReview` 不再需要用户手动选。

任务进行中进度文案区分 pass：
`[1/2] 主引擎转写…` → `切换模型，释放显存…` → `[2/2] 副引擎复核…` →
`正在整理补漏建议…`。
完成后汇总汇报：「主稿 N 条 / 第二列 M 条 / 新增 K 条补漏建议」；随后：

- 主稿进核对台；
- 自动打开/提示「双引擎复核」可查看第二列（只读）；
- 质检队列出现「双引擎补漏」分组，逐条采纳/跳过；
- 报告新增一节：两稿条数、only_b 数、采纳数、两 pass 耗时与内存。

## 9. 失败与取消

| 场景 | 行为 |
| --- | --- |
| Pass A 失败 | job=error，主稿不变（不写回） |
| Pass A 成功、内存闸门不足 | job=error，主稿**保留**，提示关闭应用/只跑主引擎 |
| Pass B 失败 | job=done，`secondary_error` 写明原因；主稿与 A 的质检队列保留，不生成 ensemble |
| Pass B 运行中用户取消 | **只中止 B**；Pass A 已完成的字幕正常写回核对台，job=done（`secondary_cancelled=true`），提示「主稿已完整保留，副引擎已取消」 |
| Pass A 运行中取消 | job=cancelled，不写回半份主稿（沿用现有单引擎语义） |
| 两个 pass 之间取消 | job=cancelled，主稿已入核对台；不启动 B |
| 第二列已有旧稿 | Pass B 覆盖第二列（与现有手动流程一致），不碰主稿 |

## 10. 验收

**功能**

- 一次任务产出主稿 + 第二列 + ensemble 队列；
- 与主稿任意字幕时间重叠 ≥20% 或 ≥0.15s 的候选**永远不出现**在 ensemble 队列；
- 远距离重复短句不会被误杀；±5s 内同文重复会被去重；
- ensemble 命中空白 missed/coverage 时只保留一条升级后的卡；
- Pass B 取消后主稿完整、可正常导出；
- 第二列只读（DualView 无编辑入口）；
- 采纳一条 ensemble 后，核对台多一句，历史多一步，⌘Z 能撤回；
- 交换主/副后默认 VAD 仍正确（Qwen→Silero，Whisper→WhisperSeg）。

**数字**（Test 二 918.1s）

- 主 Qwen + 副 Whisper：主稿 CER 11.47%、副稿 CER 10.67%、only_b 建议数记录在报告；
- 主 Whisper + 副 Qwen：主稿 10.67%、副稿 11.47%；
- 两 pass 顺序耗时 ≈ 56s + 60s + 释放/加载 ≈ 130–150s，峰值 RSS 不超过单引擎峰值 +1GB；
- 8GB 机器任务开始前即拒绝（注入 `total_ram_gb=8` 单测）；16GB 机器不因 Pass A
  后的 `available` 偏低被误拦；
- 两个 pass 共享同一份 16k WAV（用 `audio_cache.ensure_wav` 调用次数断言）；
- 区间 dual 只改范围内的第二列（范围外条目逐字不变）。

### 真机实测（Test 二 918.1s，2026-11-20）

- 主 Qwen（Silero）92 条；副 Whisper（WhisperSeg）105 条；顺序耗时 **120.6s**；
- Pass A 后可用内存 **16.7GB**（48GB 机器），未被硬拦；释放/加载正常；
- 副稿 only_b 经时间排重 + 局部去重 + 纯发声过滤后，**2 条**补漏建议：
  `139.96s 必要だね…`、`851.40s いいよ…`；与主稿无时间重叠；
- 质检队列：5 条 coverage + 2 条 ensemble，没有同一处双卡；
- 报告新增【双引擎协同】section，headline 为「主稿 92 条 / 第二列 105 条 / 新增 2 条补漏建议」。
