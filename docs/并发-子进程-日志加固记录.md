## 1. 目标与约束

这三件事的共同目标是让“失败、取消、并发”变成**可预期、可解释、可回收**的状态，而不是靠用户重启应用。

约束：

1. **不改变识别结果**：VAD/ASR/对齐/断句参数一律不动；
2. **不改变 UI 主流程**：仍然是“上传 → 开始转写 → 核对 → 导出”；
3. **单卡单模型**：进程内两个引擎各占 3–4GB，不能为了并发而复制引擎；因此采用“单槽 + 会话归属”，而不是允许多任务并行；
4. **改动可单点回退**：取消令牌、子进程执行器、日志配置分别独立。

## 2. 并发隔离

### 2.1 旧实现的问题

```python
CANCEL_EVENT = threading.Event()   # 模块级单例
...
CANCEL_EVENT.clear()               # 每个任务开始都清
...
cancel_event=CANCEL_EVENT          # 所有任务共用
...
finally:
    if thread.is_alive():
        CANCEL_EVENT.set()         # 任何窗口的断开/停止都打这个事件
```

后端 `default_concurrency_limit=4`，所以：

- A 窗口点「打断」→ B 窗口的转写被停；
- A 开始新任务 `clear()` → B 已发出的取消被抹掉；
- 两个任务的 `ENGINE.last_stats/last_missed_spans/last_align_stats` 互相覆盖；
- 首次同时转写 → 两个线程各自 `from_pretrained` 一份 3–4GB 权重。

### 2.2 新实现：`jobs.py`

```python
class CancelToken:
    job_id: str
    session_hash: str
    label: str
    finished_at: float | None
    # .cancel() / .is_set() / .wait() / .short_id()

class JobRegistry:
    start(session_hash, label) -> CancelToken   # 已被占用则抛 JobBusy
    finish(token) -> bool                       # 只有当前持有者能释放
    cancel_for_session(session_hash) -> (bool, str)
    busy_reason() -> str
```

语义：

| 场景 | 结果 |
| --- | --- |
| A 正在转写，B 点「开始转写」 | B 收到“已有任务在运行（A 的任务）”，不启动 |
| A 正在转写，B 点「中途打断」 | B 收到“另一个会话正在转写…已忽略”，A 不受影响 |
| A 正在转写，A 点「中途打断」 | 只取消 A 的令牌，引擎在下一个检查点停下并保存已完成字幕 |
| A 的任务结束后 B 再开始 | 正常启动 |
| A 客户端刷新/断开 | generator 收到 `GeneratorExit` → 只 `token.cancel()`；**槽位等 worker 真正退出后**由 worker 的 `finally` 释放 |

为什么槽位不在 generator 的 `finally` 里释放：generator 可能在 worker 还在跑模型时先退出；如果此时释放，新任务会和旧 worker 同时用同一个引擎单例。让“真正停止工作的线程”释放槽位，是这里最关键的一条。

### 2.3 会话归属

Gradio 的 `gr.Request.session_hash` 通过参数注解注入：

```python
def trigger_cancel(request: gr.Request | None = None):
    ok, message = JOB_REGISTRY.cancel_for_session(_session_hash(request))
```

`transcribe_media` / `transcribe_selection_to_editor` / `manual_transcode_proxy_generator` 都加了 `request` 参数（放在 `*values` 之前，否则 Gradio 的 `special_args` 不会注入）。已用 `gradio.helpers.special_args` 对真实函数签名做断言：

- `transcribe_media`：29 个 UI inputs → 31 个实参（progress/request 各插入一个）；
- `transcribe_selection_to_editor`：29 → 30（request 插入）；
- `manual_transcode_proxy_generator`：2 → 3。

### 2.4 顺带修掉的 progress 跨线程

旧代码在 worker 线程里调用 `progress(ratio, desc=...)`，而 `gr.Progress` 绑定请求上下文；状态更新本来已经通过 `queue` + generator `yield` 完成，这一行既冗余又不安全。

现在：

- worker 的 `cb()` 只 `q.put(("progress", ...))`；
- generator 线程收到 progress 项后再调用 `progress()`；
- 调用异常只记 `debug`，不影响状态卡片。

## 3. 子进程生命周期

### 3.1 `procutil.py`

```python
run_command(cmd, *, timeout=None, cancel_event=None) -> CompletedProcess
```

实现要点：

- `Popen(stdout=PIPE, stderr=PIPE, text=True)` + 两个 daemon 读线程，避免管道写满死锁；
- 轮询 `cancel_event` 与 deadline；
- 取消/超时：`terminate → wait(3s) → kill → wait(3s)`；
- 抛 `CommandCancelled` / `CommandTimeout`，异常对象带 `stderr` 尾部；
- 非零返回码不抛异常，交给调用方判断（保持 ffmpeg 主/回退命令的原有语义）。

所有外部命令统一走它：

| 位置 | 是否可取消 | 超时 |
| --- | --- | --- |
| `transcribe.decode_wav_16k` | ✅ 取消令牌从引擎传进来 | 1800s |
| `audio_cache.ensure_wav` | ✅ 透传 | 同上 |
| `manual_transcode_proxy_generator` 标准压制 | ✅ `GeneratorExit` → finally terminate | 由进程自身结束；wait(10s) |
| `create_m4pro_hardware_proxy` 回退链 | ✅ 传入 cancel_event | 1200s / 1800s |
| `_media_duration_and_peaks` ffprobe | ❌（20–30s 短命令） | 30s |
| 波形直读 ffmpeg pipe | ❌（180s 短命令，输出是二进制 f32le） | 180s |

### 3.2 取消解码

`decode_wav_16k` → `extract_audio_16k` → `load_audio_for_transcription` 全链路增加 `cancel_event`：

- 引擎在 `transcribe_file` 里捕获 `CommandCancelled`，置 `last_interrupted=True`，返回 `[]`；
- 上层 `transcribe_media` 会得到“转录已取消，尚未生成有效字幕”的明确状态，而不是等 ffmpeg 自己结束；
- `audio_cache.ensure_wav` 的 partial 文件名从 `{pid}` 升级为 `{pid}.{uuid8}`，同进程并发不再互相覆盖；取消/异常时 `finally` 删除 partial。

### 3.3 代理压制

- 正式成片先写 `{stem}_{size}_preview.part.mp4`，成功后 `os.replace` 成 `..._preview.mp4`；
- 触发路径的 `finally` 会 `terminate_process(proc)`，然后删除 partial；
- 历史代理只认最终文件名，partial 不会被 `get_existing_proxy` 误复用；
- 标准压制失败后回退链也写同一个 partial，成功后原子替换；
- 平台分流：macOS 才尝试 `h264_videotoolbox`；Linux/Windows 直接用 `libx264`，不再先白等两次失败；
- 失败时把 ffmpeg stderr 尾部写日志（原来 `stderr=DEVNULL`，用户只看到“压制失败”）。

实测：

- 60s/1080p 片段，标准压制 ~4.1s，产出 26MB 代理；
- 在第二次 `next(gen)` 后 `gen.close()`：日志出现“客户端断开，终止代理压制”+“终止代理 ffmpeg pid=…”，partial 和正式文件都不存在，`_PROXY_JOB_ACTIVE=False`；
- UI 点击「压制 480p 代理」成功切换 `reviewer-video` 的 src。

## 4. 日志

### 4.1 落盘

`logging_setup.setup_logging(OUTPUT_DIR / "logs")`：

- `outputs/logs/kikusub.log`，5MB × 3 轮转，UTF-8；
- 同时输出 stderr，开发时仍能看到；
- 格式：`时间 级别 [线程名] logger: 消息`；
- `httpx/httpx2/gradio/huggingface_hub/...` 压到 WARNING，避免遥测请求刷屏；
- `threading.excepthook` 记录后台线程未捕获异常。

### 4.2 关键事件

| 事件 | 日志字段 |
| --- | --- |
| 启动 | python / platform / device / torch / transformers / gradio / root / log / 模型目录 |
| 转写开始 | job / session / media / engine / slice |
| 转写完成 | job / cues / chars / elapsed / interrupted / out |
| 转写失败 | job / session / media / engine + **完整 traceback** |
| 取消 | session / job / 是否真的取消 / 拒绝原因 |
| 选区转写 | job / session / media / 时间范围 / row |
| 代理压制 | session / media / size / 方案 / rc / stderr 尾部 |
| 客户端断开 | job / session / 终止的 ffmpeg pid |

UI 错误卡片现在会附一行：`详情已写入 outputs/logs/kikusub.log`。

实测一条静音片段错误的日志：

```
ERROR [kikusub-transcribe-4b496089] kikusub: 转写失败 | job=4b496089 | ...
Traceback (most recent call last):
  File ".../app.py", line 1116, in worker
    raise RuntimeError("未检测到有效语音。...")
RuntimeError: 未检测到有效语音。...
```

### 4.3 运维建议

- 用户报障时只需要 `outputs/logs/kikusub.log`（最近 15MB）；
- 日志里含本地文件名/路径，不建议公开上传；
- 轮转文件 `kikusub.log.1/2/3` 由 `RotatingFileHandler` 管理，不需要手动清理。

## 5. 行为变化（用户可感知）

1. **同一时间只允许一个转写任务**。第二个窗口点「开始转写」会明确提示“已有任务在运行”，而不是排队、卡住或互相打断。
2. **「中途打断」只作用于当前窗口发起的任务**。别的窗口点它不会误伤。
3. **刷新/关闭标签页会取消自己的任务**，但不会影响另一个还在跑的窗口。
4. **解码阶段也能被取消**（以前要等 ffmpeg 解码完）。
5. **代理压制断连会杀 ffmpeg**，不再留下孤儿进程/半成品。
6. 出错时界面会告诉你去哪里看日志。

## 7. 已知边界

1. **模型前向不可中断**：取消只在“解码 / 分段循环 / 对齐段之间”生效。一次 `generate` 或一次 16s 窗口的对齐如果已经在跑，要等它返回。这是 PyTorch 推理的固有边界，不在本次范围。
2. **回退代理链**（`create_m4pro_hardware_proxy`）在阻塞执行期间无法响应窗口断开，只能等当前命令超时；标准路径（带 `-progress` 的流式压制）可以立即终止。
3. **槽位可能被“卡在模型前向”的任务占住**，直到该 forward 返回；这是“宁可拒绝新任务，也不让两个任务共用一个引擎”的取舍。
4. 选区转写仍是同步函数，不是流式 generator；本次只保证它能被单槽隔离和取消，进度条/异步化留待 P2-3。
5. 单进程单槽；如果未来要做“多用户/远程部署”，需要把 JobRegistry 扩展到按模型实例分池，而不是简单去掉单槽。
