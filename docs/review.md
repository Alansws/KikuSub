# 合入前自审清单

> 用途：**把改动合入 `main` 之前**，或**交给用户验收之前**，逐条过一遍。
> 这份清单替代"让另一个模型再 review 一遍"——本项目固定用单一模型开发，所以要靠
> **固定的检查动作**补上"换一双眼睛"的效果，而不是靠临场发挥。
>
> 针对的是"长期项目里 AI 一定会犯的错"，不是代码风格。风格交给 `ruff` / `tsc`。

---

## 0. 什么时候用

- 改完一个功能、准备合入 `main` 时；
- 修完一个用户报障、准备交付时；
- **不需要**在每次小改动上跑——那就变成新的形式主义了。

---

## 1. 四件事（笔记里的 Review 口径，落成本仓库可执行的问法）

逐条给 **通过 / 不通过 + 证据**。没有证据的"通过"等于没做。

### ① 业务是否真的跑通了

- [ ] 有一条**用户能走通**的路径被证明过：命令、测试名、或截图（三选一，写出来）。
- [ ] 涉及界面的改动：`bash tools/shots/capture_matrix.sh --compare docs/images/shots/baseline`
      跑过，或按 `AGENTS.md` 红线 10 手点过单击跳转 / 抖动单击 / 缩放 / 保存。
- [ ] 涉及 Python 的改动：`pytest -q` 绿，且**新行为有会红过的用例**（写出来是哪个）。

### ② 实现是否够优雅

- [ ] 没有"为了绕过问题"加的第二套实现（同一个事实只有一个来源）。
- [ ] 没有自造轮子：`procutil.run_command`（子进程）、`core/subtitles`（时间码/格式）、
      `core/i18n`（双语排版）、`server/deps`（共享依赖）这些已有基建用上了没有？
- [ ] 没有 fallback / 死代码：加"兜底"之前先问"这条路径真的会发生吗"；改了几版留下的旧实现删掉。

### ③ 测试是否有意义

- [ ] 新增的用例**删掉之后会有人疼**（不是 `assert 1 + 1 == 2` 那种）。
- [ ] 没有为了让测试变绿而放宽断言（把 `==` 改成 `in`、把精确值改成范围）。
- [ ] 重型用例（截图矩阵、打包、全量 pytest）没有塞进默认的快速回环。

### ④ 有没有充分复用已有基建

- [ ] 如果新写了一个"通用"函数/组件，先回答：仓库里现成的是哪个？为什么它不够用？
      （答案写进提交信息，不然下一个人会再写第三份。）
- [ ] 样式：没有新增裸 px（间距走 `var(--sp-N)`）、没有新增裸色值（走令牌）。
      `npm run test:main` 里的 style-drift 用例盯裸 px；`npm run check:svelte` 盯 `.svelte` 的类型。

## 2. 本仓库的四条硬检查

- [ ] **红线**：`AGENTS.md` §4 的 10 条有没有踩（内核边界、提案唯一实现、单槽并发、
      断句要数字、历史一条线、主题令牌、导出走 `setExport*`、改 Python 重打 sidecar）。
- [ ] **验证顺序**：`pytest -q` → `python -m core.smoke` → `cd desktop && npm run check`
      → `npm run build` → `npm run test:main`（改界面再加截图比对）。
- [ ] **文档同步**：改了什么行为 → `AGENTS.md` 索引 / `docs/contracts/` 对应那一份要不要改？
      新增/删除文件 → 文档里的路径还对不对？（**错误的文档比没有文档更可怕**。）
- [ ] **提交按层**：`core,server` / `desktop` / `docs` 各自成 commit，混在一起就等于放弃回滚粒度。

## 3. 单模型下的三个补偿动作

单一模型自审最容易"顺着自己的思路再读一遍，然后觉得都对"。三个动作专治这个：

1. **隔一轮再读**：改完先做点别的（或先跑测试），再回来看 `git diff`。第一遍读的是"我
   想写的东西"，第二遍才能读到"实际写下的东西"。
2. **给置信度**：每个"我改好了"的判断标 0–100。**≥90** 才按原方向继续；**<60** 就要考虑
   这个功能是不是本身就难做——笔记里的口径是"两个强模型都打不到 60 分，说明功能本身难"，
   单模型下等价于"自己都说服不了，就别硬修"。
3. **换个入口找问题**：不要从"我改了什么"出发，从"用户会怎么用坏它"出发——
   空字幕、同名文件、取消到一半、200% 缩放、切走再切回。

---

## 4. 别把两件事混了

- **合入 `main`**：过完上面第 1–3 节就够了。合入本身不要求版本号、tag、sidecar 是最新的
  ——那不是发版。
- **发版**：额外满足 `docs/release.md` 的四步，至少先跑

  ```bash
  bash tools/release/preflight.sh --with-tests
  ```

  它会拦：版本号没 bump（tag 已存在）、还没合入 `main`、sidecar 过期、工作区不干净。
  改动还没合入 `main` 时它必然报错，这是对的——发版本来就该在 `main` 上做。
