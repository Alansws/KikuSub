# 双引擎复核与工作流重构（需求稿 · 2026-11）

> **状态：需求稿，未动工。** 本文是给「下一次会话」的交接文档：先读它，再读
> [日语引擎优化路线-2026-11.md](日语引擎优化路线-2026-11.md)（已完成的引擎侧工作）与
> [contracts/](contracts/) 里的对应契约。
>
> **一句话**：把「一个引擎出稿 → 人工逐条核对」升级成「主引擎出稿 → 人工核对（可对单句
> 叫第二引擎）→ 可选地把另一引擎的整片稿放进第二列做 diff 对照 → 双源 AI 润色定稿 →
> 翻译 → 导出」，并按这个顺序重整左侧导航。
>
> **本稿覆盖的三个决定**（来自 2026-11-14 的产品讨论）：
> 1. **删掉批量复核入口**（「复核 N 条」「复核选区」）；多选代码保留，单句复核保留。
> 2. **新增「双引擎复核页」**：第二引擎的整片稿进第二列，逐条 diff 高亮，可选择采用。
> 3. **AI 润色支持双源**：同时参考两版字幕给终稿；翻译仍在原文定稿之后，不受影响。

## 1. 目标工作流（用户视角，按顺序）

### 流程 A：单引擎，人工把稿子做干净（现有主线，不变）

1. 导入 → 转写（引擎 A）→ 进核对台。
2. 清质检队列、逐条试听、框选局部「转写选区」修正。
3. 某一句拿不准时，点「🎧 用另一引擎再听一遍」——省掉
   「删掉这句 → 在波形上重选框 → 回顶部换引擎 → 点转写选区」这一串动作。
4. 原文满意后 → 润色（单源）→ 翻译 → 导出。

### 流程 B：双引擎对照（本稿新增）

1. 先按流程 A 用引擎 A 转出一版（进核对台）。
2. 在**转写页换引擎 B 再整片转一次**。
3. 由于核对台已有 A 的稿、且引擎不同，**B 的稿不进核对台**，而是进「双引擎复核」页的第二列，
   并提示「已放入双引擎复核 · 第二引擎 B」。
4. 复核页两列并排，**像 git diff 一样**逐条标出：
   - `=` 两边一致；`~` 同一句但文本不同（逐字高亮差异）；`+` 只有 B 有（A 漏句）；
     `−` 只有 A 有（B 漏句）。
5. 用户逐条决定：采用 B 这一句 / 保留 A / 暂时不动；也可整列采用（危险操作，二次确认）。
6. 回到润色：AI 同时拿到 A、B 两版文本，给出**终稿**提案（仍可复制提示词到外部模型跑完粘回来）。
7. 原文定稿后 → 翻译 → 导出。

> **翻译不受影响**：翻译永远只吃「定稿后的原文一列」，不参与双引擎比较（沿用 D-3/D-4）。

### R2 单句复核（保留并小修）

- 入口：检查器「当前条目」+ 质检「低置信」条目（现状保留）。
- 建议补一个**与双栏的联动**：如果当前句在第二列有对应句，单句复核卡片应显示「B 列文本」
  而不是临时调用第二引擎——避免同一件事两个入口给两套结果。**待拍板（Q6）**。

### R3 双引擎复核页

**数据**

- 每个会话可以有一份「第二版本」：`Session.alt_review`（结构见 §3.1），**不进 `history`**。
- 它属于参考文档，不是核对基线：编辑永远发生在核对台（列 1），复核页只做「看」与「采用」。

**页面**

- 独立页面（侧栏可发现），两列：
  - 列 1：核对台当前版本（只读展示；点某句 = 在核对台定位并选中）。
  - 列 2：第二引擎版本（只读；标注引擎名、转写时间、条数）。
- 顶部：匹配统计（一致 X / 不同 Y / A 独有 Z / B 独有 W）、「只看差异」开关、
  「整列采用」「丢弃第二列」。
- 行内：`=`/`~`/`+`/`−` 状态徽标；`~` 行做**逐字 diff**（新增/删除字符高亮）；
  每行一个「采用 B 这句」按钮（写回核对台，一步历史，可撤销）。
- 空态：没有第二版本时说明「在转写页换一个引擎再转一次即可生成对照」。

**行为**

- 第二版本存在时，侧栏「双引擎复核」出现徽标（差异条数）。
- 采用 B 的句子 = 在核对台做一次 `updateCue`（沿用单句复核的采用路径，一次历史）；
  整列采用 = 一次批量历史（沿用 D-5 的精神：一次撤销退回）。
- 丢弃第二版本 = 删 `alt_review`，核对台零变化。

### R4 双源 AI 润色

- 提案契约扩展（**先改契约，再改代码**）：
  - 源文本从「一列」变成「两列」：`source` 加 `digest_a` / `digest_b`（或 `digest` 覆盖两列拼接）；
  - 条目载荷 `{i, text_a, text_b}`；模型输出仍是 `{i, after}`（终稿）；
  - 校验：两列条数/序号必须一致；digest 任一不符 → 409，字幕零变化；
  - 单源时行为完全不变（两列退化成 `text_b` 为空）。
- 提示词模板新增变量 `{{SRT_A}}` / `{{SRT_B}}`；默认模板要写明「两版都是同一段音频的转写，
  以更准确的一版为准，不要拼接两版产生重复内容」。
- 外部粘贴路径同样支持双列（复制提示词时把两列都带上；粘贴回来的终稿走同一个提案校验）。
- 应用仍然是整批一次历史（D-5）、不碰时间码（D-1）、列满全部条目（D-6）。

### R5 导航与页面结构（按工作流顺序）

建议顺序：

```text
导入 → 转写 → 核对台 → 双引擎复核 → 润色 → 翻译 → 导出
（底部）提示词库 · 设置
```

- 「AI 优化」拆成**润色**与**翻译**两个页面（用户明确说「两个按钮挤在一起」要改）。
- 润色页只做润色（单源/双源）；翻译页只做翻译（吃定稿原文）。
- 双引擎复核页只在有第二版本时可点（或隐藏），避免空页。
- 迁移旧入口：`AiView` 里的「润色/翻译」seg 按钮改为页面级；`setAiKind` 的调用点一并处理；
  快捷键与 `⌘1..⌘5` 若与视图绑定需要重新排（**待拍板 Q7**）。

## 3. 设计草案（给人拍板用，不是最终实现）

### 3.1 第二版本的数据结构与接口

```python
# server/sessions.py（示意）
@dataclass
class AltReview:
    engine: str                 # whisper / qwen / ...
    cues: list[SubtitleCue]
    source: dict                # {job_id, at, media_path}
    created_at: float
```
- `Session.alt_review: AltReview | None = None`；**不进 HistoryState**（它是参考文档）。
- 接口（新）：
  - `GET /api/alt-review` → `{engine, count, source, cues?}`（cues 可分页，整片可能上千条）；
  - `DELETE /api/alt-review` → 丢弃；
  - `POST /api/alt-review/apply` → `{indices: [...], mode: "single"|"all"}` 把 B 的文本写回核对台
    （**走会话的统一历史**，一次提交；返回应用后的快照）。
- 转写路由规则（`server/routes_jobs.py`）：
  - 核对台为空 → 照旧覆盖（第一版本）。
  - 核对台非空、**引擎与本轮不同**、且请求带 `alt_review=true`（转写页勾选/确认）→ 结果写入
    `alt_review`，**不动 `review_cues`**，任务结果里带 `{alt_review: true}` 供前端提示。
  - 核对台非空但引擎相同 → 照旧覆盖（重转同一引擎 = 替换第一版本），或**待拍板 Q4**。
  - 默认值建议：转写页出现「放进双引擎复核（不覆盖当前稿）」的勾选项，**默认勾上**（当核对台
    已有稿且引擎不同），用户可取消改成覆盖。

### 3.2 匹配与 diff（`core/dual_review.py`，纯函数）

- 输入：列 1、列 2 的 `SubtitleCue` 列表。
- 步骤：
  1. 按时间重叠候选配对（重叠 > 0）；
  2. 在候选里按文本相似度（归一化后 `difflib.SequenceMatcher` 比率）取最大且过阈值（建议 0.45）；
  3. 剩余未配对：看时间区间里是否「至少有一半落在对方两行之间」→ 判为漏句（`+`/`−`）；
  4. 输出 `{pairs: [{a_index, b_index, kind: 'same'|'diff', ratio}], only_a: [...], only_b: [...]}`。
- 逐字 diff：`char_ops(a, b)` → `[{op:'eq'|'del'|'ins', text}]`，前端渲染高亮。
- 要求：纯函数、无模型、进 CI（`tests/test_dual_review.py`），边界用例：
  - 一句被对方拆成两句（不能全判成 diff）；
  - 时间整体偏移 0.2 s（仍要配得上）；
  - 空列表 / 一边为空。

### 3.3 提案契约改动（`core/ai_proposal.py`）

- `build_proposal(texts=...)` → 增加 `texts_b`（可选），`source` 里同时落两份 digest。
- 生成入口（in-app 分块、外部粘贴）都要能带两列；`validate_proposal` 同时校验两列条数与 digest。
- 提示词渲染：`core/prompts.render(prompt, {"SRT": ..., "SRT_A": ..., "SRT_B": ..., "LANG": ...})`
  （现有变量名要兼容，单源模板不变）。
- 验收沿用 A1–A8，新增：
  - A9：双源提案应用后 `(start,end)` 仍逐条精确相等；
  - A10：只改 B 列 digest → 409 且字幕零变化。

## 5. 风险与取舍

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 两次整片转写的时间轴不同 | VAD/分窗差异会让同一句错开 0.1–0.5 s | 匹配以「时间重叠 + 文本相似度」双条件，不只看时间；用例覆盖整体偏移 |
| 第二版本很长 | 830 s 素材约 85–105 条；47 分钟长片可能上千条 | 接口支持分页/区间；页面虚拟滚动（现有表格已有虚拟滚动可参考） |
| 会话历史膨胀 | 第二版本不进 history；采用才进（一次一步） | 明确写入规则；丢弃走独立接口 |
| 行数预算 | `store/ReviewView` 只许变短 | 新页面独立组件 + `lib/` 纯函数；接线时只动少量行 |
| 单槽任务 | 第二次整片转写仍与转写共用单槽 | 沿用 `JobRegistry`，转写页提示「正在转写」 |
| AI token 翻倍 | 双源输入约为单源两倍 | 分块大小可调；提示词里只放两版原文，不放历史提案 |
| 引擎相同再转 | 是「替换第一版」还是「第二列」有歧义 | 见 Q4，建议按「替换第一版」并显式确认 |
| 「采用 B」与润色冲突 | 采用 B 后 A 的文本消失，提案 digest 变化 | 提案前校验 digest（现有 409 机制），采用后需要重新生成提案 |
