## 0. 结论先行

这个项目的**转录主链路已经相当成熟**：VAD 合并、能量谷吸附、空段重试、CTC 逐字对齐、断句 DP、撤销重做、监看代理、详报面板都有真实实现，不是“演示壳”。第三轮把全片 CER 压到 22.46%，说明“识别效果”这条线已经进入边际收益很低的阶段。

真正的短板在**产品化与工程化**，按优先级排：

1. **并发语义是错的**（P0）：`CANCEL_EVENT` 是全局单例、两个引擎也是全局单例，而后端 `default_concurrency_limit=4`。两个标签页同时转写时，停止 A 会打断 B，A 清空取消标记也会让 B 无法被停止；首次同时加载模型还会各自加载一份 3–4GB 权重。
2. **“无语音”被当成“整段送模”**（P0，已修）：VAD 未命中时两引擎都会 `segments = [(0, len(audio))]`。静音/雨声/纯音乐会被 Whisper 幻觉成字幕；30s 的静音测试段实际生成了「すぅう…」「ずぅ…」两条假字幕，而且这个兜底会绕过 `max_segment_s`。
3. **失败与取消的边界不干净**（P0/P1）：解码 ffmpeg 没有超时，取消只在分段循环里检查；客户端断开后代理生成的 ffmpeg 子进程会变成孤儿；模型加载没有锁。
4. **Qwen 断句仍会劈词**（P1）：同一段 60–90s 素材，Whisper 给出 8 条、Qwen 给出 5 条，但 Qwen 出现「空 / は」「匂い / を」「好き / で」等词内切分。根因之一是 `_apply_pauses` 把“≥0.12s 的帧间空隙”一律当成可自由切分点，覆盖了助词/汉字转假名的语言成本；单纯调大阈值也只是把「空|は」换成「好き|で」，不是真修复。
5. **可观测性与可回归性不足**（P2）：`app.py` 6.3k 行单体、JS 内嵌、没有测试、评测台 `tools/eval/` 被移出版本库；出问题只能靠用户截图和 `str(exc)`。

本次已在分支上落地 **5 个低风险修复 + 32 个回归测试**（详见 §5），并验证两引擎在“有声段”行为不变、在“无语音段”不再产生幻觉。

## 2. 实测基线

### 2.1 两引擎同段对比（30–95s，真实电影对白）

| 指标 | Anime Whisper | Qwen3-ASR + CTC |
| --- | --- | --- |
| 耗时（含首次加载） | 15.4s | 12.5s |
| 字幕条数 | 13 | 12 |
| 逐字对齐 | 无（按字数分配） | 6/6 段完成，145 字，插值 9 字 |
| 典型输出 | `こういうことを、` / `2ヶ月前高校に入るまで俺は知らなかった` | `こういうことを、二ヶ月前、` / `高校に入るまで、俺は知らなかった` |
| 明显问题 | 分句偏碎（`子供の頃…` / `空はもっと…` / `ずっと近かった`） | 识别错字「な二人の匂い」；幻觉「進撃」；60–90s 出现「空 / は」「匂い / を」「好き / で」词内切分 |

结论：**Whisper 的文本更稳，Qwen 的时间轴/断句框架更强但当前语言成本被 pause 覆盖**。两者都不是“换一个就全好”，产品上应保留双引擎并让用户按素材选择。

### 2.2 性能观察

- 46 分钟全片 16k 波形：1.34s / 8000 bins，落盘约 32KB `.npz`；冷启动也可接受。
- 150s 1080p HEVC → 480p H.264 代理：约 6s（VideoToolbox 硬件路径）。
- 音频缓存命中后，重复载入几乎是瞬时。
- Qwen 每个分段实际跑了**两次音频编码器**：`_transcribe()` 里 `apply_transcription_request + generate` 一次，`align()` 里 `_encode_audio + _encoder_features` 再一次。这是目前最确定的性能浪费（见 P1-3）。

## 3. 问题清单

> 标注：**已修** = 在 `review/audit-fixes` 中已改并测试；**开放** = 建议后续处理。
> 行号以当前分支工作区为准，函数名可用于定位。

### P0 正确性 / 数据风险

#### P0-1 无语音段被整段兜底送模 → 幻觉字幕【已修】

- 位置：`transcribe.py:1176`（Whisper）、`qwen_ctc.py:847`（Qwen）
- 旧逻辑：`if not segments: segments = [(0, len(audio))]`
- 证据：用测试片段 0–30s（VAD 判定 0 个语音段，RMS 0.035、峰值 0.85，属雨声/环境声）执行全流程，产出：
  - `00:00:00,000 → 00:00:16,154 すぅう…`
  - `00:00:16,154 → 00:00:30,000 ずぅ…`
- 附加风险：该兜底绕过 `max_segment_s`（Whisper 上限 29s、Qwen 16s）。若整片 VAD 全灭，46 分钟音频会被一次性送模，基本等于 OOM/长时间卡死。
- 修复：VAD 为空时直接返回空结果并给出进度提示，由 `transcribe_media` 统一提示「未检测到有效语音」。修复后同一段 0 条字幕；有声段 8 条不变。
- 备注：纯数字静音（全 0）在旧逻辑下 Whisper 也会返回空，所以这个 bug 只在“有能量但非语音”的雨声/音乐/底噪上稳定复现——恰好是电影片头、OP/ED、环境声最常见的形态。

#### P0-2 SRT 时间戳在 59.9996s 处生成非法 `00:00:60,000`【已修】

- 位置：`transcribe.py:441` `format_srt_timestamp`
- 旧实现只对 `millis == 1000` 做 `secs += 1`，没有处理秒→分、分→时的进位。
- 复现：`format_srt_timestamp(59.9996) == "00:00:60,000"`，`3599.9996 == "00:59:60,000"`。
- 影响：浮点累加/四舍五入在句尾很容易落到 `x.9996`；一旦落上，播放器/剪辑软件会拒绝该条或整体解析失败。
- 修复：先换算成整数毫秒再 `divmod` 分解，天然处理所有进位。

#### P0-3 同名片源被替换后复用旧代理 → 画面与字幕错位【已修】

- 位置：`app.py:1405` `get_existing_proxy`
- 旧逻辑：标准代理名含文件体积，但“历史代理”回退分支用 `glob(f"{stem}_*_preview.mp4")` 后**只按修改时间取最新**，不校验体积。
- 场景：用户把 `EP01.mkv` 换成另一版（同文件名、不同内容），打开工作台 → 命中上一版代理 → 字幕对的是新片、画面是旧片。
- 修复：历史分支只接受文件名中 `_{size}_preview.mp4` 与当前 `stat().st_size` 一致且 >50KB 的候选；不匹配则回到原片。
- 后续建议：命名里加入 `mtime_ns` 或内容哈希；更彻底的是代理压制完成后写 sidecar JSON（源路径/体积/mtime/时长），复用前校验。

#### P0-4 全局取消事件 + 全局引擎 = 多会话串扰【已修，2026-11】

- 位置：`app.py:176` `CANCEL_EVENT = threading.Event()`；`app.py:977` 每次任务开始 `CANCEL_EVENT.clear()`；`app.py:6349` `default_concurrency_limit=4`；`ENGINES`/`ENGINE`/`QWEN` 都是模块级单例。
- 具体后果：
  1. 标签页 A 正在转写，标签页 B 点「中途打断」→ A 被取消（用户以为只停了 B）。
  2. A 开始新任务时 `clear()` 会把 B 的取消标记清掉 → B 的「打断」按钮失效。
  3. 两个任务并发时 `engine.last_stats / last_missed_spans / last_align_stats` 互相覆盖，报告里的“漏句/对齐统计”可能来自另一个任务。
  4. `ANIME_WHISPER` 的 `generation_config`、`Qwen` 的 `_model` 被并发读写；首次同时加载会各自加载一份 3–4GB 权重。
- 建议：
  - 取消令牌改为**每次调用创建**的对象（`CancelToken`，内含 `Event`），通过 `gr.State` 或请求上下文传递；不要用模块级 Event。
  - `run_btn`/`transcribe_selection` 设 `concurrency_limit=1`，或在应用层做“同一时间只允许一个转写任务”的显式队列，并把“已有任务在跑”反馈给用户。
  - 模型加载用 `threading.Lock` 双检；单例的 `last_*` 改成每次调用返回的 `Result` 对象，不要挂在引擎上。

#### P0-5 客户端断开/取消后，ffmpeg 子进程可能成为孤儿【已修，2026-11】

- 位置：`app.py:5162` `manual_transcode_proxy_generator` 的 `try/finally`（`app.py:5316`）只把 `_PROXY_JOB_ACTIVE=False`，没有 `proc.terminate()`；`create_m4pro_hardware_proxy` 用阻塞 `subprocess.run`（`app.py:1454/1476/1496`），无法取消。
- `transcribe.py:489` `decode_wav_16k` 的 `subprocess.run` 没有 `timeout`，取消事件也传不进去；用户点「打断」后如果卡在解码阶段，要等 ffmpeg 自己结束。
- 影响：反复刷新/关闭标签页会留下多个 ffmpeg 同时写同一个代理文件；半成品一旦 >50KB，下次会被 `get_existing_proxy` 当成“可用代理”复用（P0-3 的另一面）。
- 建议：
  - 代理生成写 `.part` 临时文件，`ffprobe` 校验时长/流后再原子 rename；`finally` 里 `terminate → wait(3) → kill`。
  - 解码用 `Popen` + 轮询 `cancel_event`，或至少加 `timeout` 与 `-nostdin`。
  - 压制前 `_drop_broken_proxy` 已有，但失败路径要覆盖客户端断开（`GeneratorExit`），不仅是 ffmpeg 返回非 0。

### P1 质量 / 性能

#### P1-1 Qwen 断句：`_apply_pauses` 把词内空隙变成免费切点【已修（启发式 + 评测台），2026-11】

- 位置：`qwen_ctc.py:350` `_apply_pauses`、`qwen_ctc.py:739` 调用点、`qwen_ctc.py:321` 的 `JAPANESE_PARTICLES` 判定。
- 机制：CTC 对齐后每个字的 `start == end`（40ms 帧粒度），字与字之间的空白帧只要 ≥ `min_pause_s`（默认 0.12s）就被判为 pause；`_apply_pauses` 把该边界的成本直接置 0，覆盖了 `_break_costs` 里“助词后 1.2 / 汉字转假名 2.5 / 词内 35”的语言成本。于是 DP 只剩时长/字数约束，容易在「空|は」「匂い|を」「好き|で」下刀。
- 实测（60–90s，只改 `min_pause`）：

  | pause 阈值 | 条数 | 输出 |
  | --- | --- | --- |
  | 0.12（默认） | 5 | `子供の頃、空` / `はもっと、ずっと近かった` / `だから、空の匂い` / `を連れてきてくれる雨は好きで、` / `雨の朝は…` |
  | 0.25 | 3 | `子供の頃、空はもっと、ずっと近かった` / `だから、空の匂いを連れてきてくれる雨は好き` / `で、雨の朝は…` |
  | 0.35 | 3 | 同上 |

- 结论：**调大阈值不是修复**，只是把“切助词”换成“切て形”。2026-11 已用“助词前/活用尾前禁止 + 假名间默认禁止 + 词例外表”实现启发式词边界（30–330s 劈词代理 2→0、CER 不变；块均准确率 −2.2pt 是取舍），详见 `P1-1-P1-3-P2-3-执行记录.md`。真正的通用修法是给 DP 一个词边界来源：
  - 轻量：用 `fugashi`/`SudachiPy` 分词，词内边界成本设 `BREAK_FORBIDDEN`，词间按品词给成本；词典可打包成小 JSON，避免引入大依赖。
  - 或：维护“动词活用尾/助词/て形”模式表，至少禁止在 `て/で/に/を/は` 前切（当前 `_break_costs` 只在“前一个字是助词”时给低分，方向反了）。
- 另外：`JAPANESE_PARTICLES` 里的多字词（から/まで/より）现在由 `MULTI_PARTICLES` + `_starts_with_multi_particle` 处理，不再依赖单字 `in` 判断。

#### P1-2 非对白段仍会产生短幻觉【已加固（复核+标记），2026-11】

- 证据：Whisper 60–90s 输出第一条 `…死ね`，参考字幕此处无台词；Qwen 在 58.48s 输出 `進撃`。
- 现有 `_retry_suspicious` 只校验“空段重试”的结果，不对主解码结果做门控；`chunk_level_stats` 已记录 peak/rms，但只用于漏句告警降噪。
- 建议（按保守程度排序）：
  1. 从 Whisper pipeline 取 `no_speech_prob`/`avg_logprob`（当前没有拿分数），对“低置信 + 短时长 + 低能量”的 cue 打标而不是直接删；核对台用颜色标出“疑似幻觉”，让用户一键删。
  2. 对纯音乐段（VAD 置信度低、谱平坦度高）跳过送模，或在报告里明确“该段为音乐/环境声，未识别”。
  3. 不要用“死ね/進撃”这类词表硬过滤——对动画台词误杀率不可控。

#### P1-3 Qwen 每段跑两次音频编码器【已修，2026-11】

- 位置：`qwen_ctc.py:630` `_transcribe`（`apply_transcription_request` + `generate`）与 `qwen_ctc.py:657` `align`（`_encode_audio` + `_encoder_features`）。
- 同一段音频的 `audio_tower` 前向做了两遍；16s 窗口下这是 Qwen 侧最大的一块可省算力。2026-11 已实现特征复用，30–330s 实测 19.8s → 16.59s（约 16%，含加载），输出逐字节相同；30–630s 为 33.73s。
- 本次实现：`_transcribe(capture_audio=True)` 先跑一次 `get_audio_features`，generate 期间把 `model.model.get_audio_features` 临时指向缓存；`_align_projected` 直接复用。失败自动回退二次编码。

#### P1-4 模型加载无锁，首次并发会加载两份权重【已修，2026-11】

- 位置：`transcribe.py:1068` `AnimeWhisperEngine.load`、`qwen_ctc.py:568` `QwenCtcEngine.load`；`_pipe`/`_model` 检查后直接加载，没有锁。
- 单槽 `JobRegistry` 已避免 UI 上的并发转写；但直接调用（脚本/未来多任务）仍可能两个线程同时看到 `None` → 各自 `from_pretrained`，3–4GB × 2。
- 建议：模块级 `threading.Lock` + 双检；加载失败要清空半初始化状态，避免下一次直接 `ready=True` 但实际不可用。

#### P1-5 `progress()` 在 worker 线程里调用【已修，2026-11】

- 位置：`app.py:1007` `def cb(ratio, message): progress(ratio, desc=message); q.put(...)`，`worker()` 在 `threading.Thread` 中执行。
- Gradio 的 `Progress` 绑定请求上下文；跨线程调用即使当前版本不报错，也不是受支持的用法。状态更新已经通过 `q.put` + generator `yield` 到 `transcribe_progress`，`progress()` 这行是冗余的。
- 建议：删除 worker 里的 `progress()`，只保留 `q.put`；如果要用原生进度条，在 generator 线程里调用。顺带能减少一条潜在的“进度双源”问题（与 AGENTS 里压制进度那条经验同源）。

#### P1-6 音频解码没有超时/取消【已修，2026-11】

- 位置：`transcribe.py:489` `decode_wav_16k` 的 `subprocess.run(cmd, capture_output=True, text=True)`。
- 损坏文件、网络盘、ffmpeg 等待 stdin 都可能永久阻塞；`CANCEL_EVENT` 在 `_transcribe_array` 的分段循环里才检查，解码阶段完全不响应。
- 建议：`subprocess.run(..., timeout=...)`；大文件用 `Popen` + 轮询取消；加 `-nostdin`。

#### P1-7 音频缓存临时文件名只用 PID，同进程并发会互相覆盖【已修，2026-11】

- 位置：`audio_cache.py:94`
  `partial = target.with_name(f"{target.stem}.{os.getpid()}.part.wav")`
- 同一进程内两个请求解码**同一个缓存键**（两个标签页同文件、或核对台与转写同时触发）时，partial 路径相同；两个 ffmpeg 同时写，`os.replace` 竞争，可能得到半截 wav 或一方 rename 失败。
- 建议：`uuid4().hex` 或 `threading.get_ident()` 加入后缀；落盘后 `sf.info` 校验采样率/帧数，再 rename。

#### P1-8 数据类默认值与 UI 默认值漂移【开放】

- `transcribe.py:261` `WhisperVadConfig` 的默认：`speech_pad_ms=150`、`min_silence_ms=200`、`min_speech_ms=100`、`merge_gap_s=0.5`、`max_segment_s=20.0`、`cue_pad_s=0.0`、`enable_loudnorm=True`。
- UI 默认：`200 / 150 / 120 / 0.30 / 12.0 / 0.02 / False`（`app.py:5450` 起）。
- 走 UI 时以 UI 为准，所以用户看到的报告是对的；但任何直接 `WhisperVadConfig()` 的脚本/测试/评测台会得到另一套行为，文档里“默认值”也会对不上。
- 建议：让 dataclass 默认值成为唯一事实源，UI 从 defaults 生成；或在 `build_whisper_config` 注释里明确“UI 覆盖默认值”，并加一个测试断言两边一致。

### P2 产品体验

#### P2-1 预设下拉预选第一个预设，但并不会应用它【已修】

- 位置：`app.py:5364`
- 旧行为：`value=preset_choices_list()[0][1]`。默认引擎是 Anime Whisper，而第一个预设常常是 Qwen 方案；界面同时显示“Qwen 预设已选中”和“Whisper 生效参数”，用户会误以为参数已切换。

#### P2-2 `beforeunload` 只要加载了字幕就拦截刷新【已修，2026-11】

- 位置：`app.py:3803`
- 行为：只要 `cues.length > 0`，刷新/关闭标签页就弹“离开此网站？”；导出后也一样。真正的编辑已经通过 `_save_draft_and_progress` 自动写盘，这个提示更多是骚扰。
- 建议：维护 `dirty` 标记（只在“表格有未保存编辑/单行编辑未提交”时置 true），或直接去掉（自动草稿已覆盖）。

#### P2-3 局部选区转录是同步阻塞、无进度、无取消【已修，2026-11】

- 位置：`app.py` `transcribe_selection_to_editor`
- 历史现状：直接调用 `engine.transcribe_file`，没有 `progress_cb`、没有 `cancel_event`；长选区（几分钟）会把该事件占满。
- 本次实现：generator + worker 线程 + queue，按 10 个输出组件 yield `⏳ 选区识别 [x%]`；复用 `JobRegistry` 取消令牌；事件侧 `show_progress="hidden"`。UI 已实测可入轨、可取消、按钮会恢复。

#### P2-4 磁盘与缓存没有产品级管理【已修，2026-11】

- `outputs/` 只增不减：SRT、`.autosave_draft.srt`、`.progress.json`、`.missed.json`、`web_proxies/`、`.cache/audio`、`.cache/peaks`。
- `audio_cache` 有 4GB prune，peaks 有 128 个上限；**web_proxies 没有上限**，上传临时文件也没有清理（Gradio 的 `max_file_size=10gb` 意味着单个上传可能复制 10GB 到 temp）。
- 建议：设置页加“打开输出目录 / 清理转写缓存 / 清理代理 / 清理上传临时文件”，显示当前占用；对 `web_proxies` 按 LRU 限制；启动时清理 `.part` 残留。

#### P2-5 代理压制把 macOS 硬件路径写死【已修，2026-11】

- 位置：`app.py:1446` 起 `create_m4pro_hardware_proxy`
- 在 Linux/Windows 上先尝试 `-hwaccel videotoolbox` + `h264_videotoolbox`，必然失败，再尝试“软解 + videotoolbox 硬编”，再失败，最后才走 `libx264`。每次白等两个失败的超时/日志；`stderr` 被 `capture_output` 吞掉，用户看不到原因。
- 建议：`sys.platform == "darwin"` 才走 VideoToolbox；其他平台直接 `libx264`/`h264_nvenc`（探测 `ffmpeg -encoders`）；失败时把 `stderr` 最后 20 行写进状态卡片。

#### P2-6 浏览器编解码兼容性没有检测【已修，2026-11】

- 实测：原始 MKV（HEVC 10-bit）在 Chromium 中 `videoWidth=1920`、`error=null`，但 `canPlayType('hvc1')` 为空，画面黑屏；界面没有任何提示，只有用户自己猜“是不是卡了”。点“压制 480p 代理”后 6 秒恢复。
- 建议：`loadedmetadata` 后检查 `video.canPlayType(videoType)` / `video.videoWidth === 0` / `video.error`，在 `proxy_status` 或画面上给出“当前浏览器无法解码该编码，点『⚡ 压制 480p 代理』”；或在导入时就调用 `ffprobe` 读 `codec_name/pix_fmt`，提前提示。

#### P2-7 模型管理仍是“首次运行自动下载”【部分修复】

- 已修：`app.py:19` 改为 `os.environ.setdefault("HF_ENDPOINT", ...)`，尊重用户已有的镜像/官方端点；`NO_PROXY` 改为合并而不是覆盖。
- 仍开放：
  - `app.py:11-15` 无条件 pop 掉所有 `HTTP(S)_PROXY`，企业代理/需要代理下载模型的用户会直接失败；建议只对 localhost 设 `NO_PROXY`，不要全局删代理，或提供 `KIKUSUB_KEEP_PROXY=1`。
  - 没有模型管理 UI（查看大小、删除、切换路径、重新下载）；`QwenCtcEngine.model_available` 只检查 `config.json`，缺 shard 时也会认为“已就绪”，要到 `from_pretrained` 才报错；建议校验 `model.safetensors.index.json` + 全部 shard，或 `snapshot_download` 的完整性标记。
  - 下载进度只到“正在下载…”级别；`snapshot_download` 支持 `tqdm` 回调，可以接进度条。

#### P2-8 产品边界：单文件、无批量、无项目工作区【开放，按需求排序】

当前是“一次一个文件 + 平铺的 outputs 文件”。从“工具”走向“产品”，我认为最有价值的三个方向（按投入产出）：

1. **项目/工作区**：保存 `媒体路径 + 当前字幕 + 参数 + 校对位置 + 代理选择` 为一个可 reopen 的 session；现在这些信息散落在 `outputs/*.progress.json`、`monitor_last.json`、presets，并且按 stem 命名会撞车（见 P3-5）。
2. **批量队列**：同一个预设跑多集，输出统一命名、失败重试、队列可暂停；动漫/剧集用户是天然批量场景。
3. **翻译/双语对齐**：当前定位是“日语转写”，但“转译”需求真实存在；如果做，建议作为独立后处理（保留日语时间轴，按 cue 翻译），不要动 ASR 链路。

说话人分离、字幕压制、i18n 可以再往后排；`README` 的“已知限制”里已经写明，不属于“代码缺陷”。

补充一个实测细节：导入官方中日双语 SRT 后是 **997 条独立记录**（482 个时间轴块 × 日/中两行），画面叠加能正确聚合为两行，但编辑日文行不会同步修改中文行。若“双语成片”是目标场景，建议增加「同时间轴多行联动编辑」与「按语言过滤表格」；当前更适合作为“日语转写 + 人工翻译”的单语工作流。

#### P2-9 响应式与视觉细节【开放，低优先级】

- 1280px 宽度下右侧“字幕核对”按钮会换行成“撤回/清理标点”“重做”“清空”三行，视觉上松散；可给按钮组设 `min_width` 或在小屏折叠成菜单。
- 没有深色模式；`CSS_CUSTOM` 里大量硬编码 `#0f172a`/`#f8fafc`。
- “全片转录原始结果”折叠面板默认展开，与下方“核对时间轴全景”是两张字幕表，新用户容易分不清哪张是“最终结果”。建议明确命名（“本次转写结果（只读）” vs “核对基线（可编辑）”），或把只读表收进 Tab。

#### P3-6 JS/CSS 内嵌在 Python 字符串，缺少静态检查【已修，2026-11】

### 最后一点建议

不要急着继续压 CER。以当前 22.46% 的全片基线，下一轮真正的收益更可能来自：

1. **让失败可见、可取消、可恢复**（并发、日志、断点、磁盘）——这是用户信任的地基；
2. **Qwen 断句的词边界**（配合可复现的评测台）——这是“读起来像人写的字幕”的关键；
3. **项目/批量工作流**——这是从“单次转写工具”变成“日常生产力工具”的分水岭。

如果只能做一件事：先做 **P0-4 + P0-5 + P3-4**。它们不改识别质量，但会显著减少“用户以为坏了/卡死了/结果串了”的支持成本。
