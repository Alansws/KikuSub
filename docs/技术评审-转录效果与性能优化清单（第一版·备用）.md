## 1. 结论速览

**三条真正的地基**（决定成品字幕质量的地方，按影响力排序）：

1. **分段层**——"VAD 合并 + 最长时长硬切"。它决定了模型**听到什么**，比模型本身更早地决定了上限。
2. **时间轴层**——CTC 逐字强制对齐 + 日语断句动态规划。它决定了**字幕怎么切、什么时候出现**。
3. **后处理层**——缝合、去重、重叠裁剪、空行清理。它决定了**成品能不能直接用**。

界面交互、波形手感、撤销栈这些是"用起来顺"，不是"做得对"。本文不涉及。

## 2. 核心卖点的技术底座

把"卖点"还原成机制，才能判断哪条是真壁垒、哪条只是包装。

### 2.1 音频层：一切精度的物理起点

| 卖点 | 实际机制 | 含金量 |
|---|---|---|
| 全本地推理 | 权重懒加载到 `models/`，`HF_ENDPOINT` 走镜像 + `snapshot_download` 断点续传；设备自动 `MPS → CUDA → CPU`，`PYTORCH_ENABLE_MPS_FALLBACK=1` 兜住不支持的算子 | **工程壁垒**。同类工具大多卡在"装不上、下不动" |
| 时间区间转写 + 原片绝对时间轴 | `-ss` 输入侧快进（关键帧级）+ `-t` 限长，再叠加 `time_offset` 还原绝对时间 | 中。逻辑简单，但"切片后时间还对得上原片"是很多工具做错的地方 |
| 弱人声增强 | `dynaudnorm=f=150:g=15:m=10.0:r=0.9:b=1` 单声道下混 + 峰值归一化（`max_amp < 0.4` 时拉到 0.85） | 中。**是双刃剑**，见 A/B4 |
| 波形与监看 | 服务端 1kHz 解码出峰值数组（2400–8000 bins）+ 前端 Canvas（DPR 适配、`requestAnimationFrame` 播放线、`fastSeek` 松手才跳） | 中。技术不难，但"长片拖拽不卡"是真实体验分水岭 |
| 兼容性兜底 | 480p 代理压制三级回退：VideoToolbox 硬解硬编 → 软解硬编 → libx264 ultrafast | 中。解决 MKV/HEVC 浏览器黑屏这个真实痛点 |

### 2.2 分段层：最被低估的地基

`Silero VAD → 按 gap 合并 → 按最长时长硬切（切点吸附能量谷）`（`transcribe.py:661-743`）。

这条链决定了送进模型的音频**边界在哪**。Whisper 与 Qwen 都吃"一段干净、边界落在停顿处"的输入；边界一旦落在音节中间，模型输出必然缺字或复读——这是模型能力之外的系统性损耗，也是本文认为**性价比最高的优化位置**。

评审时指出的两个缺陷，现已全部处理：

- **硬切与内容无关** → ✅ 已修（A1）：`_energy_valley_cut`（`transcribe.py:609-642`）在目标切点前 0.4s 内找能量最低点吸附，`_cut_keeps_segment_count`（`644-659`）保证吸附不会凭空多切一段；`CUT_SNAP_S=0` 可整体回退。
- **`speech_pad_s` 是死参数** → ✅ 已修（问题 2）：参数与两处实参已删除，并在 docstring 里写清"留白由 Silero 的 `speech_pad_ms` 在 VAD 阶段并入段边界"，避免再次误导。

### 2.3 时间轴层：项目的真差异化

**引擎 B（Qwen + CTC）** 的技术含量集中在这里：

- **单次前向同时拿文本与发声帧**：`audio_tower` → `multi_modal_projector` → 自研 `CtcAlignmentHead`（LayerNorm → Linear 降维 → ConvTranspose 2× 上采样 → 4 层膨胀残差卷积 → 分类头）→ `torchaudio.functional.forced_align`。
- **时间分辨率 40ms 是硬事实**：encoder 帧 80ms × upsample 2。这是 head 训练时定死的，不是实现选择（见 N2）。
- **帧—时间映射**按 100 mel 块分段计算 `_conv_length`，处理了变长 padding，不是简单的 `i * 0.04`。这段代码是整个仓库里最容易写错、也写得最对的一段。

**断句层**才是真正难复制的资产（`qwen_ctc.py:233-449`）：

- 切点代价：句末标点 −6（鼓励切）、逗号 0、句中 35（强烈不鼓励）、助词后 1.2、汉字→假名 2.5、**禁则 1000**（小假名、长音符、ASCII 词内、片假名连写、汉字连写、敬语前缀+汉字、"ま"+"す/せ/し"、35 个禁切词）。
- 停顿证据：CTC blank 连段 ≥ `min_pause_s` 的位置，把代价降到 0（`_apply_pauses`）。**这是"声学证据覆盖语言学先验"的设计，方向是对的。**
- 动态规划：段数基础代价 0.1 + 超软上限 1.5/秒 + 超硬上限 3.5/秒 + 超字数 1.2/字，DP 求全局最优。

这套东西的价值在于：**它把"ASR 文本"变成了"可播字幕"**。模型再准，断句断在「ありがと／う」上也是废的。这是本项目相对"套个 Whisper 出 SRT"的工具最实质的差距。

**引擎 A（Whisper）** 的时间轴是明确的近似：段边界来自 VAD，段内按 `3.0 + 字数` 加权比例分配（`transcribe.py:830-845`）。README 已经诚实标注了这一点——这也是 B1 想解决的问题。

### 2.4 后处理层：成品可用性的最后一公里

- `_heal_broken_cues`：按"下一句以小假名/长音开头""汉字接汉字""片假名接片假名"等 9 条规则缝合被劈开的词（`qwen_ctc.py:942-1008`）。
- `_dedupe`：排序 + 重叠裁剪（前句尾部截到后句起点）+ 再缝合一遍。
- 纯标点/纯省略号清理：`*.clean.srt`。

方向正确，但**缝合规则偏激进**（见 3.1 问题 6）。

### 2.5 工程可靠性层

可取消（`threading.Event` + 队列轮询 + `GeneratorExit` 时兜底置位）、增量抢救（`*.part_cancelled.srt`）、自动草稿 + 断点、预设原子写入（`presets.py`）、全参数留痕报告。

这一层不产生"效果"，但决定"敢不敢拿它处理两小时的片子"。**它比大多数单点优化更值钱，改动时要格外小心不要破坏**（N7）。

## 4. 转录效果的剩余优化空间

模型固定，但"模型听到什么、听到多长、什么时候被切、切完怎么拼"全在代码里。以下按杠杆排序。

### A1｜硬切点改为能量谷吸附 ★最高优先

- **改前形态**：超过 `max_segment_s` 的语音段按固定步长机械切断（该逻辑已由 `_energy_valley_cut` 取代，见下方"改法"；当前实现位置 `transcribe.py:609-642`，调用点 `661-743`）。
- **为什么影响效果**：日语里「っ」促音、长音「ー」、拨音「ん」、无声化母音都只有几十毫秒。刀口落在中间，模型拿到半个音节，输出缺字；Whisper 还容易因此触发复读。
- **改法**：在目标切点 ±0.4s 内，用 10–20ms 帧算 RMS（纯 numpy，无需模型），取局部能量最低点作为实际切点；不越过相邻 VAD 段边界。能量平坦（连续说话）时退化为原切点。
- **成本**：低（约 40 行）。**收益**：切点处吞字率下降。**风险**：低。
- **验证**：统计切点落在能量 10% 分位的比例；对 20 个含长句片段做 A/B 看首尾字错误率。

### A2｜解码上下文外扩（Qwen 先行）

- **现状**：送模音频 = VAD 段本身。VAD 的 `speech_pad_ms` 是固定值，而句首辅音（k/s/t/p）能量低，VAD 常在辅音**之后**才触发。
- **后果**：「そんな」→「んな」，句首假名系统性丢失。
- **改法**：送模时前后各多给 150–250ms（clamp 到相邻段中点）；因为 Qwen 有 CTC 逐字时间，可以按"首字起点"精确裁掉外扩部分，不会带进多余文本。
- **注意**：Whisper 路径**不要**先做这个——没有字级时间，外扩会直接带进幻觉文本。等 B1/B2 落地后再考虑。
- **成本**：中。**收益**：句首字准确率。**风险**：中（裁剪逻辑要严格）。

### A3｜空结果段自动重试 ★

- **现状**：`if not text: continue`（`transcribe.py:1090`、`qwen_ctc.py:842`）。
- **为什么重要**：VAD 判定"这里有人说话"但模型一个字没出——这恰恰是最需要人看的地方，现在被静默吞掉了。用户只会在成品里"感觉少了一句"，无从定位。
- **改法**：对空结果段做一次重试：增益 +6~9dB（若原始峰值接近 1.0 则改为 −6dB 防削波）→ 再解一次；仍为空则写入"疑似漏句区间"清单，进报告并在核对台标出来。
- **成本**：低。**收益**：直接提升召回，且把静默失败变成可操作信息。**风险**：低（只对空结果生效，不影响正常段）。

### A4｜幻觉闸门 + 统一后处理层 ⛔ 已排除

> **状态：已排除。** 实测两个模型均经过动漫/影视语料微调，未出现「ご視聴ありがとうございました」类音乐段幻听，该项不成立，不执行。

- **现状**：只有 `REPEATED_CHUNK_RE`（6 次以上重复单元折叠）和纯标点清理。纯音乐段 Whisper 会输出「ご視聴ありがとうございました」「おやすみなさい」；也会把上一句整段复读。
- **改法**：在"引擎输出 → 分句"之间插一层 `postprocess.py`：
  - **段级**：字/秒 > 12（日语正常语速约 5–7 字/秒）判可疑；`speech_s/seg_s` 低但文本长判可疑。
  - **文本级**：常见幻觉句正则表（可配置，不写死在代码里）；与上一句完全或近似重复判可疑。
  - **字符级**：标点归一（重复「。。」、「、、」→ 单）、长音符/波浪线统一、去模型自带说话人标签。
  - **关键设计**：**可疑项标记而不是静默删除**，进报告让用户决定。误杀「はい」连说两次这种合法重复的代价，比放过一条幻觉更大。
- **成本**：低-中。**收益**：成品可信度。**风险**：中（误杀）。

### A5｜断句 DP 加可读性约束 ★

#### A5.0 现状（已核对当前源码）

`partition_cues`（`qwen_ctc.py:390-449`）的代价累积在 `413-449`，只有四类**上限**：

| 项 | 阈值 | 罚分 | 代码 |
|---|---|---|---|
| 软超时 | `soft_max_dur=3.8s` | `(dur-3.8) × 1.5` | `427-428` |
| 目标超时 | `max_dur=4.3s` | `(dur-4.3) × 3.5` | `429-430` |
| 超字数 | `max_chars=21` | `(n-21) × 1.2` | `431-433` |
| 硬超时 | `hard_max_dur=5.2s` | 直接 `continue`（不可行） | `424-425` |

切点代价的尺度是**非对称**的，这是加下限时必须对齐的坐标系：

```
句末标点 −6.0（切了反而"赚"）  ← 负代价，是短条目的主要来源
逗号      0.0
助词后    1.2
汉字→假名 2.5
句中     35.0（几乎不敢切）
禁则   1000.0（绝对不切）
每多一条 +0.1（SEG_BASE_COST）
```

**结论一：短条目不是"缺下限"直接造成的，而是"句末 −6.0 + 每条只收 0.1"造成的。** DP 遇到「。」就白拿 6 分，切出一条 0.3s 的「はい。」几乎零成本，所以 `_cues_from_alignment`（`708-713`）才需要在事后用 `min_cue_dur=0.35` 硬拉——那是**补丁，不是约束**。

**结论二：cps 罚分如果照原方案直接写成 `cost += (cps - 6.5) * k`，方向是反的。** 因为代价是按"每条"累加的，而 cps 在切分前后近似不变（同一段音频的字数除以时长），所以切成 2 条会**交两份**罚分、合成 1 条只交一份。DP 会为了省罚分而倾向于**合并**——正好是可读性的反方向。这是这类"密度型"目标函数在分段 DP 里的经典陷阱，必须用有界形式压住。

**结论三：A5 治不了"21 字 / 0.6 秒"。** 那个数字是**对齐塌缩**（CTC 把太多字压进太少帧）的产物，声学跨度本身已经错了；再聪明的切分也无法在 0.6s 里变出 2.3s 的显示时间。A5 能做的是"不要在助词处吝啬那一刀"，真正的补救是 A6 把它标出来 + B6 二分重试。**原文档把这一条写成"A5 可解"是过度承诺，此处更正。**

#### A5.1 改法

**新增常量**（`qwen_ctc.py:245-250` 常量区，与 `SEG_BASE_COST` 等并列）：

```python
MIN_CUE_DUR_FLOOR = 0.80   # 单条字幕最短可读时长（秒）
CPS_READABLE = 9.0         # "能读"的下限：字/秒，用于反推最短时长
CPS_COMFORT = 6.5          # "读得舒服"的上限：字/秒
DUR_DEFICIT_COST = 3.0     # 时长缺口：每秒罚分
CPS_EXCESS_COST = 0.9      # 语速超额：每字罚分
CPS_EXCESS_CAP = 6.0       # 单条 cps 罚分上限，防止"靠合并掩盖密度"
```

**在 `partition_cues` 的代价累积末尾追加**（紧接 `433` 行之后，`if cost < best[j]` 之前）：

```python
n_chars = j - i
if n_chars > max_chars:
    cost += (n_chars - max_chars) * OVERRUN_COST   # 顺手用回 234 行已定义、433 行却硬编码 1.2 的常量

# —— 下限一：时长缺口 ——
if dur > 0:
    need = max(MIN_CUE_DUR_FLOOR, n_chars / CPS_READABLE)
    if dur < need:
        cost += (need - dur) * DUR_DEFICIT_COST

    # —— 下限二：语速超额（按"多出来的字数"计，且有单条上限）——
    excess = max(0.0, n_chars - CPS_COMFORT * dur)
    cost += min(excess * CPS_EXCESS_COST, CPS_EXCESS_CAP)
```

净增约 10 行，`partition_cues` 签名不变，所有调用点（`683-685`）无需改动。

**权重不是拍出来的，是对着上表的尺度校准的：**

| 场景 | 时长缺口 | cps 罚 | 合计 | 行为 |
|---|---|---|---|---|
| 0.35s / 2 字（现状最碎的一条） | `0.8-0.35=0.45 → 1.35` | `2-2.28<0 → 0` | **1.35** | 恰好抵消一次助词切分（1.2+0.1），但仍敌不过句末 −6，所以「はい。」「え？」这类合法短句**照样能独立成条** |
| 1.0s / 3 字（「はい。」） | 无缺口 | `3-6.5<0 → 0` | **0** | 完全不受影响——这是必须保住的行为 |
| 3.0s / 21 字 | 无缺口 | `21-19.5=1.5 → 1.35` | **1.35** | 轻微偏好"再切一刀"，观感改善 |
| 0.6s / 21 字（病态） | `2.33-0.6=1.73 → 5.19` | `17.1 → 6.0`（封顶） | **11.19** | 会在**助词/标点**处补切，但 11.19 < 35（句中禁切），**绝不在词中间下刀** |

关键点：`DUR_DEFICIT_COST=3.0` 与现有硬超时罚分 3.5/s 同量级，让"太短"与"太长"对称。再验一次最坏边界：`0.3s / 21 字` 时两项合计 `(2.33-0.3)×3 + 6 ≈ 12.1`，只有 `BREAK_MID_PHRASE=35` 的三分之一、`BREAK_FORBIDDEN=1000` 的 1.2%——所以**不会为了让一条字幕变长而破坏词边界**。这是这条改动唯一的红线，权重必须守住这个不等式；一旦调大到让罚分越过 35，DP 就会开始在词中间下刀，宁可不要这个约束。

#### A5.2 与事后补丁的衔接

`_cues_from_alignment`（`708-713`）的 `min_cue_dur=0.35` 硬拉逻辑**保留不动**，但要明确它的角色变化：

- 走 DP 的路径：DP 已保证 `dur >= 0.8`（除非物理上不可能），这段逻辑基本成为死代码；
- 走 `_cues_fallback` 的路径（对齐降级）：`split_text_into_cues` 的 `min_guard = min(seg_dur/n, 0.45)`（`transcribe.py:842`）仍需要它兜住。

顺带修一个现有的边界问题：`712` 行 `end = min(wanted, max(ceiling, start + MIN_CUE_DUR))` 在 `ceiling < wanted` 时会把 `end` 顶到 `ceiling`，即**把与下一条之间的间隙全部吃掉**。加了下限后这条路径触发频率会大幅下降，但建议同时把 `max(ceiling, ...)` 改成 `min(ceiling, wanted)` 的语义（"最多借到下一条起点"），避免极端情况下两条字幕首尾完全相接、播放器看起来像"没换行"。

#### A5.3 A5-b：把禁则表抽出来给 Whisper 用（顺手解决问题 4）

`_break_costs`（`262-339`）里的字符级禁则（小假名、长音符、ASCII 词内、片假名连写、汉字连写、敬语前缀、35 个禁切词）目前只服务 Qwen 的 DP。抽成一个纯函数：

```python
def forbidden_cut_positions(text: str) -> bytearray:
    """返回长度 len(text)+1 的布尔表：1 表示该位置禁止切分。"""
```

`_break_costs` 改为查表（顺便就是 P7），Whisper 路径的 `split_text_into_cues`（`transcribe.py:794-867`）在逗号再切之后**仍超 `max_cue_chars`** 时，用同一张表找最近的合法切点做硬兜底。这样：

- 问题 4 得到修复，且两条引擎的断词规则一致；
- **只做"超长兜底"，不给 Whisper 引入 DP**——Whisper 没有字级时间，任何 DP 都只能按字数比例编时间，反而制造"看起来精确的假时间轴"。

#### A5.4 成本 / 收益 / 风险 / 验证

- **成本**：低。`qwen_ctc.py` 约 25 行（含常量与 A5-b 抽函数）；`transcribe.py` 约 15 行（Whisper 超长兜底）。
- **收益**：观感层面最直接的一条，**一个字文本都不改**（`costs` 只影响"在哪切"，不影响"切出什么字"）。典型改善：长句不再出现"半秒闪 20 字"，短促应答仍然独立成条。
- **风险**：低但非零。唯一真实风险是权重失衡——若 `DUR_DEFICIT_COST` 被调到 12 以上，就会开始为了凑时长而拆句末标点，出现"一句话被拆成两条"；若 `CPS_EXCESS_CAP` 取消，病态段会主导目标函数、把相邻正常段一起拽成一条。**这两个数不要随手改，改前先跑 A5.4 的三步验证。**
- **验证**（不改模型、不需要 GPU）：
  1. 拿 `outputs/` 里已有的 Qwen 字幕，离线重跑 `partition_cues`（喂同一份 `char_spans` + `costs`），对比新旧切分结果：统计"条数变化 / 最短条时长 / cps 的 P50 与 P95 / 在句中位置被切的比例"。**在句中位置被切的比例必须为 0**，这是红线。
  2. 人工抽 30 条改动过的条目，只看"读起来是否更顺"，不看文本。
  3. 复跑 `outputs/测试用_言叶之庭.mkv` 全片，比较条数与总字符数——**总字符数必须完全相等**。

**实测结果（已执行，2026-10-26）**

**① 离线对拍**：同一批 `char_spans` + `costs` 分别喂新旧 `partition_cues`，5 个合成场景（每个场景用固定 cps 排字、标点处插 0.18s 停顿）：

| 场景 | 条数 旧→新 | 最短条时长 旧→新 | max cps 旧→新 | 禁切点下刀 |
|---|---|---|---|---|
| 通常对白 | 2 → 2 | 0.43s → **1.14s** | 7.0 → 7.0 | 0 |
| 短促应答「はい。」 | 1 → 1 | 0.50s → 0.50s | 6.0 → 6.0 | 0 |
| 标点稀少长句 | 3 → 3 | 1.33s → 1.60s | 7.5 → 7.5 | 0 |
| 逗号密集 | 2 → 2 | 1.89s → 1.89s | 6.3 → 6.3 | 0 |
| 长音促音 | 2 → 2 | 0.57s → **1.86s** | 7.0 → 7.0 | 0 |

四个结论都能从这张表读出来：

1. **条数一条都没变**——可读性下限只调整"在哪切"，不制造新条目，也不并掉不该并的条目；
2. **最短条时长只在真该拉长的地方上升**（0.43→1.14、0.57→1.86），而「はい。」这类合法短句**保持 0.50s 不变**——说明下限没有粗暴地"把短的都拉长"，它只惩罚"字数多而时长不够"的条目；
3. **max cps 全部不变**——没有出现"为了凑时长把相邻条目并成一条更挤的"这种反向效果；
4. **禁切点下刀数恒为 0**，红线保持。

**② 真实片源端到端**（`测试用_言叶之庭.mkv` 300–325s，2 段）：出 6 条，时长 1.60–4.00s（平均 2.40s），77 字。**总字符数与文本一字未改**，与①的"条数不变"一致。

**③ 两条红线（断言级）**：

- `はい。`（1 条）仍独立成条——句末标点造成的合法短句不能被下限并掉；
- 病态密度（21 字 / 0.6s，模拟对齐塌缩）**仍是 1 条**，没有被"补切"成两段同样挤的碎片。这条恰恰证明了 **A5 治不了对齐塌缩**：`char_spans` 本身错时，DP 只能在错误的时间上切得更"好看"，得靠 A6 先看见、B6 再重试。

**顺带确认的一处方向性错误**：原方案按"每条"累加 cps 超额罚分，而 DP 求全局最小代价——条数越少、累加次数越少，于是目标函数**奖励合并**，与"提高可读性"的初衷相反。加 `CPS_EXCESS_CAP` 封顶后这个反转才消失。这也是 `DUR_DEFICIT_COST` / `CPS_EXCESS_CAP` 两个数不能随手改的原因。


### A6｜对齐降级可观测 ★

#### A6.0 先讲清楚：什么叫「降级」

**一句话：降级 = 逐字对齐失败后，退回"按字数比例猜时间"的近似路径。** 文本是对的，时间不再是测出来的，而是分出来的。

Qwen 引擎出字幕有两条完全不同的路，走哪条取决于 `align()` 是否成功（`qwen_ctc.py:625-700`）：

| | 正常路径（`ok=True`） | 降级路径（`ok=False`） |
|---|---|---|
| 函数 | `_cues_from_alignment`（`677-714`） | `_cues_fallback`（`716-723`） |
| 时间来源 | CTC 强制对齐，**每个字**都有真实发声帧 | `split_text_into_cues`：段内按 `3.0 + 字数` 加权**平均分配**（`transcribe.py:830-845`） |
| 精度 | 40ms（encoder 80ms ÷ upsample 2） | 段内均匀：一条 4s 的句子切成 3 条，就是 1.33s / 1.33s / 1.33s |
| 断句依据 | 语言学代价 + 停顿证据 + DP | 标点正则，切完就按比例摊时间 |

**`align()` 里 5 个不产出逐字时间的出口**（可直接核对）：

| reason | 位置 | 含义 | 是否算真失败 |
|---|---|---|---|
| `no-acoustic-chars` | `609-610` | 文本里没有可发声字符（纯符号/标点） | **否**。注意这里返回的是 `ok=True`，但 `chars` 为空，调用方仍会落到 `_cues_fallback`——统计时应单列为"无需对齐"，不能计入降级率 |
| `frame-mismatch(a!=b)` | `614-615` | 帧数与时标数组长度不一致 | 是（实现层异常） |
| `too-few-frames(n<m)` | `620-622` | 帧数不够放下所有字（含重复字需额外帧） | 是，**最常见**：快语速、长句、复读 |
| `forced-align-failed:<Exc>` | `628-635` | `torchaudio.forced_align` 抛异常 | 是 |
| `no-spans` | `657-658` | 对齐跑完但没有任何 token 拿到非空 span | 是 |

还有一层**更细、更隐蔽**的降级：`_fill_unaligned`（`372-400`）。即使整段 `ok=True`，只要有个别字没拿到 span（CTC 把它吞进 blank 了），这些字就会被插值成 `start == end` 的零宽点。**这些字的时间是编的，但整段仍算"对齐成功"。** 目前的统计完全看不见这一层。

**为什么必须可观测（而不是"知道就行"）：**

1. **用户无法自证产品承诺。** 卖点是"40ms 逐字对齐"，但成品 SRT 里看不出哪条是 40ms、哪条是平均分。用户看到一句时间偏了，无法判断是"模型听错"还是"时间估的"，只能整体怀疑工具。
2. **A/B 没有分母。** A5（断句下限）、B6（对齐失败二分重试）、P2（消除二次 encoder）三项的收益都要靠"降级率"来证明。没有这个数字，改动只能靠"感觉好一点"。
3. **降级不等于漏句，两者必须分开计数。** A3 的 `last_missed_spans` 记的是"没出文本"；A6 记的是"有文本但时间不可信"。混在一起会让两个指标互相污染。

#### A6.1 现状（已核对当前源码）

- `aligned` / `total` 只在进度回调里出现一次：`transcribe_array:829-830`，进度条一走就没了。
- `_cues_fallback` 调用处（`825-826`）把 `result.reason` **直接丢弃**，`AlignmentResult.reason` 字段就此断链。
- `AlignmentResult`（`460-466`）没有插值计数字段；`_fill_unaligned` 的返回值（`674`）也不带统计。
- 任务报告 `build_transcription_report`（`app.py:656-762`）已有【疑似漏句区间】与【切分点吸附】两节，**没有对齐相关任何一行**。

#### A6.2 改法（三段式，全部是只读统计，不改任何时间轴）

**① 引擎侧：把降级过程记下来**

`AlignmentResult` 加一个字段（`466` 行后）：

```python
interpolated: int = 0   # 本段被插值（时间靠猜）的字数
```

`align()` 结尾（`674-675`）改为：

```python
chars = _fill_unaligned(folded, chars, float(out_times[-1]))
interp = max(0, len(chars) - aligned_count)      # 见下方"口径修正"
return AlignmentResult(chars=chars, pauses=pauses, mean_logprob=mean_lp, ok=True, interpolated=interp)
```

> **口径修正（落地时发现）**：原先打算用"零宽 `end <= start`"判插值，**这是错的**。CTC 允许一个字只占 1 帧，此时 `start == end` 但它是真对齐出来的；反过来 `_fill_unaligned` 插出来的字也是零宽。两者无法区分，会把正常段误报成插值（实测端到端 `interp_chars=3/3`，即整段被误判）。正确做法是在调用 `_fill_unaligned` **之前**先记下 `aligned_count = len(chars)`，插值数 = `len(chars) - aligned_count`。

`QwenCtcEngine.__init__`（`497-507` 附近）加 `self.last_align_stats: dict = {}`，与 `last_missed_spans` / `last_segment_stats` 并列——**保持三者结构一致，上层才能用同一套写法取用**。

`transcribe_array` 里：开头重置（`738` 旁）、循环内累加（替换 `822-826`）、结尾落账：

```python
aligned = 0; noop = 0; align_chars = 0; interp_chars = 0; degraded: list[dict] = []
...

> **为什么必须是四个桶而不是三个（落地时发现）**：最初只设了 `aligned / noop / degraded` 三桶。跑真实片源（300–325s）立刻破不变量：`segments=2` 但 `aligned=1`，差的这一段既没对齐、也没降级——它是**空结果段**（模型没出字，走 `last_missed_spans` 后 `continue`）。空段属于 A3 的漏句统计，但它**同样是这 N 段里的一段**，不单独成桶，报告里"共 2 段：✅1 ○0 ⚠️0"就会对不上账。**四桶才是穷尽的**；`empty` 与 A3 的 `missed_spans` 数量一致，两个指标可互查。

**② 报告侧：新增【逐字对齐】一节**

`build_transcription_report` 加参数 `align_stats: dict | None = None`，在【切分点吸附】之后（`673` 行后）插入：

• 00:12:04.800 → 00:12:11.200  (6.40s)  no-spans  53 字
```

`✕ 空结果` 与 `生成截断` / `复读吃满上限` 三项都是**按需出现**：为 0 时整段省略，避免报告里堆一串 0。实测输出形如：

```
【逐字对齐】共 1 段：✅ 1 段完成（100.0%）｜○ 无需对齐 0 段｜⚠️ 降级 0 段｜字级插值 0/3 字（0.0%）｜复读吃满上限 1 段（非截断，已跳过重跑）
```

三种边界要写对：

- **Whisper 引擎**：`align_stats` 为空 → 固定输出"该引擎无逐字对齐，句内时间按字数比例分配"，**不能让用户误以为 Whisper 也有 40ms 精度**；
- **`use_alignment=False`**：输出"逐字对齐已停用"，而不是"0/120 段降级"（后者会被读成故障）；
- **中断任务**：降级清单只覆盖已完成段，需标注"（统计截至中断处）"。

**③ 核对台标记：建议第一版不做**

原方案提到"核对台表格对降级行加标记（可选）"。不建议第一版做，原因是它需要 `cues_to_table` 增加列、`REVIEWER_CLIENT_JS` 同步改表头与列宽、撤销/重做栈里所有 dict 结构跟着变——为一条统计信息动前端主链路，风险收益比不划算。**先用报告覆盖 90% 的需求**；若确实需要在核对台看，第二版再按"只读徽标、不进 state"的方式加。

#### A6.3 成本 / 收益 / 风险 / 验证

- **成本**：极低。`qwen_ctc.py` 约 30 行（含字段与累加），`app.py` 约 25 行（一节报告 + 参数透传）。
- **收益**：
  - 把"40ms 精度"从宣传语变成**可验证的产品承诺**（报告里能自查）；
  - 给 A5 / B6 / P2 提供唯一可信的分母；
  - 暴露"整段成功但个别字插值"这层隐形降级——这是当前完全看不见的质量缺口。
- **风险**：极低。纯新增只读统计，不参与任何时间计算；`last_align_stats` 为空时上层全部走默认分支，等价于现状。
- **验证**：
  1. 对 `outputs/测试用_言叶之庭.mkv` 跑一次，报告里的 `aligned + noop + degraded + empty` 必须等于 `segments`（四个桶互斥且穷尽，和 A1 的段数守恒是同一个思路）；
  2. 手工构造 `too-few-frames`：把 `max_cue_chars` 调到 5 再跑，降级率应显著上升，且清单里的 reason 与区间能对上实际音频；
  3. 对比 `interp_chars` 与 `align_chars`：**实测给出了一条比预期更有用的结论**。95–110s（复读段）为 `0/3`；300–325s 为 `10/68 = 14.7%`。后者远超原设想的"1% 以下"，但核查后发现不是统计口径错，而是**这段 ASR 文本本身就与音频对不上**（`例年より`→`定年より`、`梅雨入り`→`梅入り`、`活発な梅雨前線の`→`河床がばゆ前線の`）。CTC 找不到这些字的声学依据，只能插值。**所以插值率不是"CTC 头与素材域不匹配"的告警，而是"这段文本可能有识别错误"的定位器**——它把"哪几句的字幕文本不可信"直接指出来了，比降级率更细。原设想的方向说反了。

### B1｜Whisper 文本 + Qwen CTC 时间轴（混合模式）　⏸ 待定

> **状态：待定，暂不执行。** 保留技术评估，后续如需要再启动；在此之前不引入双模型驻留。

- **核心洞察**：CTC 对齐头与 ASR 模型**解耦**——它只需要 `(audio, text)`。所以完全可以用 Whisper 的文本 + Qwen 的 encoder/CTC 做强制对齐。
- **价值**：直接消掉 README 里"Whisper 句内时间是近似值"这条硬限制。两个引擎从"文本质量 ↔ 时间精度"二选一，变成"文本质量 + 时间精度"可叠加。这是本清单里**唯一能改变产品定位**的一条。
- **代价**：需同时驻留 Qwen（约 4GB）+ 每段多一次 encoder 前向；速度介于两者之间。CTC vocab 覆盖不到的汉字会变 unk，其时间靠 `_fill_unaligned` 插值（已有逻辑）。
- **建议**：做成可选开关「精确时间轴（复用 CTC 头）」，默认关，文档写清代价。不要在没跑通之前替换默认路径。

### B2｜Whisper 原生词级时间戳（B1 的轻量替代）

- `return_timestamps="word"`，transformers 用 cross-attention + DTW 出词级时间，**不需要第二个模型**。
- 前提：`generation_config` 里要有 `alignment_heads`（large-v3 微调通常保留），缺失时 try/except 回退到现状。
- 精度不如 CTC（DTW 受注意力峰值平滑影响，实测常在 ±80–150ms），但远好于"按字数比例分"。
- 速度约慢 20–40%（DTW 开销）。**若 B1 成立，B2 降级为"不想多占 4GB 内存"时的折中。**

### B3｜两行折行 + 禁则处理

- **现状**：单行输出，靠 `max_cue_chars` 控宽。成品在播放器里会被自动换行，位置不可控。
- **改法**：输出层加 `wrap_two_lines(text, 13~16 字/行)`，行首禁「、。，）」等，行尾禁「（「『」等，优先在助词/标点后断。
- **成本**：低。**收益**：成品可直接用。**风险**：极低（可选开关）。

### B4｜响度处理从"开关"升级为"模式"

- **现状**：布尔开关 → `dynaudnorm`。它是逐帧动态增益：静音处抬 BGM、响处压人声，对 ASR 是双刃剑；且滤波器状态依赖上下文，**切片与全片结果不一致**。
- **改法**：三档：`关闭` / `峰值归一化`（复用 `load_wav_mono` 现有逻辑）/ `EBU R128 loudnorm`（两遍，I=-16 LUFS, TP=-1.5）；`dynaudnorm` 保留为"强动态场景"档。
- **注意**：**不要改默认值**。默认值一改，所有历史预设的语义就变了（N4）。只加档位，并在报告里标注当前档位。

### B5｜环绕声源中置优先

- 5.1/7.1 影视源对白主要在中置声道，`-ac 1` 走 ffmpeg 默认下混会把 L/R 的 BGM 与效果声一起混进来，降低对白 SNR。
- **改法**：`ffprobe` 读 `channel_layout`；≥5.1 时用 `pan=mono|c0=0.7*FC+0.15*FL+0.15*FR`（或直接取 FC）。仅对环绕源生效。
- **成本**：低。**收益**：电影场景对白清晰度，VAD 与 ASR 同时受益。**风险**：低。

### B6｜对齐失败二分重试

- **现状**：`too-few-frames` / `no-spans` 直接整段降级为比例分配。
- **改法**：失败时按能量最低点一分为二，各自对齐；仍失败再降级。
- **成本**：中。**收益**：降低降级率，尤其快语速段落。

### 5.1 P4｜`max_new_tokens` 自适应

**状态：✅ 已执行（第二批），并在真实片源实测中修正了原方案的一处错误假设。**

**改前**：`QwenCtcConfig.max_new_tokens = 440` 原样透传给每次 `generate`。440 是给"最坏情况"留的余量，而送模窗口最长 16s（`max_segment_s`），正常日语对白 16s 最多 120–130 字，多出来的 300+ token 只在**模型复读**时才会真的被用掉。

**改后**（`qwen_ctc.py` 的 `_transcribe`）：

```python
TOKENS_PER_SEC = 12     # 日语语速上限约 8 字/秒，×1.5 余量（汉字/片假名常一字多 token）
TOKENS_HEADROOM = 32    # 句首句尾与标点的固定余量
cap = min(int(cfg.max_new_tokens), max(64, int(dur * TOKENS_PER_SEC) + TOKENS_HEADROOM))
```

实测上限：1s → 64（地板）、4s → 80、15s → 212、16s → 224、≥34s → 440 封顶。

**原方案错在哪：把"吃满上限"等同于"被截断"。**

落地后按真实片源探查，15s 段的三种典型输出：

| 区段 | 送模时长 | cap | 实际生成 | 文本 | 字/token | 真相 |
|---|---|---|---|---|---|---|
| 95–110s | 15.0s | 212 | **212** | 「ちゅる」（3 字） | 0.014 | 复读/空转，一个字都没被砍 |
| 300–315s | 15.0s | 212 | 43 | 48 字正常播报 | 1.12 | 正常，EOS 提前结束 |
| 600–615s | 15.0s | 212 | 2 | 「♪」 | 0.50 | 音乐段 |

第一行正是"撞上限"的样本。若按原方案无条件按 440 重跑，结果仍是 `cap=440 / gen=440`、文本仍是那几个字——**白烧一次完整前向**，而且会把这类段计入"截断"，污染报告里的可信度数字。

**修正后的判据**（`classify_capped`）：

```python
CHARS_PER_TOKEN_FLOOR = 0.5   # 正常日语对白约 1.0–1.7；复读实测可低至 0.014

def classify_capped(n_chars, n_gen, cap) -> tuple[bool, bool]:
    capped = n_gen >= cap
    if not capped:
        return False, False
    return True, n_chars >= CHARS_PER_TOKEN_FLOOR * max(n_gen, 1)
```

- `capped=True, truncated=True` → 吃满且密度正常 ⇒ **真被砍**：按 440 重跑一次，且**只保留更长的结果**（重跑更差不至于把已有文本弄丢）。
- `capped=True, truncated=False` → 吃满但密度塌陷 ⇒ **复读/空转**：不重跑，单独计入 `capped_repeat`。

阈值取 0.5 而非 0.6/0.8 是刻意保守：宁可多跑一次也不漏真截断；而 0.014 与 1.12 之间留了 36 倍余量，判别本身不敏感。

**报告口径**（`app.py` 的 `_align_stats_headline`）：

- `生成截断 N 段` —— 重跑后仍被砍，属**真问题**，需要人看；
- `复读吃满上限 N 段（非截断，已跳过重跑）` —— 属**模型病态**，不影响成品文本，只影响耗时。

两者分开，报告里的"截断"才不会因为复读段虚高。

**三条判断：**

1. **正常段零收益、零影响。** 生成由 EOS 提前终止，`max_new_tokens` 根本不参与——这条不是"提速项"，只是"给病态段设一道更低的止损线"。
2. **截断检测不能省，但检测本身要分清真伪。** 只降上限不检测 = 把"慢"换成"悄悄吃字"；只按"吃满"检测 = 把"复读"误报成"吃字"，还倒赔一次前向。判据必须看**字/token 密度**。
3. **12 token/秒 是估计值。** 实测正常段密度 1.12 字/token，即 8 字/秒 × 1.4 token/字 ≈ 11.2 token/秒，与 12 吻合；若后续遇到片假名长句或大量数字，应上调到 15 而非硬压。

**成本**：约 40 行（含 `classify_capped` 与报告文案）。**收益**：复读段解码步数减半（15s 段 440→212），且**不再为复读段白跑一次前向**（95–110s 段实测由"两次前向"降到"一次"）。**风险**：极低。

**验证（已做）**：

- 单元测试 15 项断言全通过：正常段 / 空段 / 恰好吃满前一 token 均不判截断；真截断（120 字 / 224 token）判截断；复读（3 字 / 212 token、1 字 / 212 token）不判截断；上限公式 1s/4s/15s/16s/30s/60s 六点核对。
- 真实模型端到端（`测试用_言叶之庭.mkv` 95–110s）：`segments=1 / aligned=1 / interp_chars=0 / truncated=0 / capped_repeat=1`，四桶守恒 `1+0+0+0==1`，耗时 16.5s（改前该段需两次前向）。

### 5.2 P6｜峰值缓存落盘 + 上限

**状态：✅ 已执行（第二批）。** 实测：46 分钟片源，冷算 0.177s（仅包络 max-abs）→ 磁盘命中 0.043s，读回结果与现算**逐元素相等**（npz 存 float32 会带浮点尾巴，读回时统一 `round(x, 2)` 才对齐）。

**改前形态（已核对）**：

- `MEDIA_PEAKS_CACHE: dict[str, tuple[float, list[float]]]`（`app.py:1054`），`MEDIA_PEAKS_CACHE_LIMIT = 8`（`1055`），`_remember_peaks`（`1075-1082`）用 `pop(next(iter(...)))` 按**插入序**淘汰——这是 FIFO，不是 LRU：命中时不会把键移到末尾，所以"反复看同一部片"的场景下它和随机淘汰没区别。
- 键构造在 `_media_duration_and_peaks:1156`：`f"{path.resolve()}_{size}"`。**不含 mtime、不含 bins、不含响度档位**。同一个路径被重新压制（size 恰好相同）会命中脏缓存；`bins` 变化时直接返回旧分辨率。
- 内存侧已经受控（原文档说的"无上限"已被修掉），**落盘仍缺**：进程重启后第一次打开核对台，要重新读 16k wav 全片算包络。

**改法**：

1. **键复用 `audio_cache`**（`audio_cache.py:41-55`）：`cache_key(media, loudnorm=False)` 已含"绝对路径 + size + mtime_ns"，与 wav 缓存天然一一对应。波形本来就固定读 `loudnorm=False` 的 wav（`app.py:1361-1364`），键的语义完全对齐。
2. **落盘**：`outputs/.cache/peaks/{key}.npz`，两个数组——`duration: float64`、`peaks: float32`（保留 2 位小数的归一化值，8000 bin ≈ 32KB/片，可忽略）。
3. **写入必须原子**：照抄仓库里已有的两种写法之一——`audio_cache.py:94-114`（`*.part` + `os.replace`，`OSError` 时退化 `copyfile`）或 `presets.py:150-159`（`mkstemp` + `os.replace` + 失败 `unlink`）。**不要直接 `np.savez(path)`**，中途崩溃会留下损坏的 npz。
4. **读取顺序**：内存 → npz（`try/except` 包住，损坏即当作未命中并删除）→ 现算。任何缓存异常都必须静默降级到"现算"，**绝不能因为缓存坏了让核对台打不开**。
5. **上限**：内存 LRU(8) 保留，但要补上"命中刷新序位"（`OrderedDict.move_to_end`）；磁盘按 mtime 淘汰到最近 128 个文件（约 4MB），或直接复用 `audio_cache.prune` 的思路写一个 `prune_peaks`。
6. **不需要额外改 `.gitignore`**：`outputs/` 已在 `.gitignore:63` 整目录忽略（`git check-ignore -v outputs/.cache/audio` 可验证），新增 `outputs/.cache/peaks/` 天然不入库。但要确认 `audio_cache.CACHE_DIR`（`audio_cache.py:22`）与新的 peaks 目录都落在这条规则下，别另起一个仓库外的路径。

**成本**：约 45 行（含 prune）。**收益**：重启后核对台免重算——2 小时片省一次全片 16k 读盘 + 8000 bin 的 max-abs 扫描（约 1–3s，机械盘更明显）；配合 P1 的 wav 缓存，二次打开接近瞬时。**风险**：极低。

**验证**：冷启动 → 打开核对台记时 → 关闭进程 → 再启动 → 再打开，第二次应无 `audio_cache.peaks` 计算耗时（加一行 debug 日志即可确认命中）；把 npz 人为截断一半，确认能正常重算而不是报错。

### 5.3 P7｜`_break_costs` 禁切点预计算

**状态：✅ 已执行（第二批）。** 落地位置在 `transcribe.py:161-203` 的 `forbidden_cut_positions`（不是当初设想的 `qwen_ctc._forbidden_word_cuts`）——因为 A5-b 让 Whisper 路径也要用同一张禁切表，函数必须上移到 `transcribe.py` 才能被两边共用。下面的"改前形态 / 改法"保留原始分析，用于追溯。
**改前形态（已核对）**：`_break_costs`（`qwen_ctc.py:283-326`）里，字符级禁则（`290-300`）是 O(1) 的相邻字符判断，但**禁切词扫描**（改前是 `313-326` 那一块，现已替换为查表）不是：

```python
for word in FORBIDDEN_WORDS:              # 35 个词
    start_search = max(0, cut_pos - len(word))
    idx = text_str.find(word, start_search)
    while idx != -1 and idx < cut_pos:
        if idx < cut_pos < idx + len(word):
            costs[i] = BREAK_FORBIDDEN
            ...
```

这段被包在 `for i in range(1, n)` 里，所以是 **O(n · W · n)**：每个候选切点都要把 35 个词各扫一遍整段文本。而且 `FORBIDDEN_WORDS` 里最短的词只有 2 字（`これ` / `それ` / `あれ` / `どれ` / `あと` / `关于` 共 6 个），2 字词在长文本里出现次数最多，`find` 的内层循环次数跟着涨；3 字词（`まして` / `ました` / `ません` / `ていた` / `ている` / `ていく` / `てみる` / `として` / `なので` / `だから` / `だけど` / `んです` / `ありま` / `お願い` 等）占绝大多数，出现频次也不低。

**改法**：把"哪些位置禁止切"一次性算成布尔表，切点查表 O(1)。

```python
def _forbidden_word_cuts(text: str) -> bytearray:
    """长度 len(text)+1 的布尔表：1 = 该位置落在某个禁切词内部，禁止切分。"""
    blocked = bytearray(len(text) + 1)
    for word in FORBIDDEN_WORDS:
        start = 0
        while (idx := text.find(word, start)) != -1:
            # 原条件 idx < cut_pos < idx + len(word)，即 [idx+1, idx+len-1]
            blocked[idx + 1 : idx + len(word)] = b"\x01" * (len(word) - 1)
            start = idx + 1
    return blocked
```

`_break_costs` 里 `313-326` 整块替换为：

```python
if blocked[cut_pos]:
    costs[i] = BREAK_FORBIDDEN
    continue
```

**等价性论证**（重构项必须先证等价）：

- 原条件 `idx < cut_pos < idx + len(word)` 展开就是 `cut_pos ∈ [idx+1, idx+len(word)-1]`，与 `blocked[idx+1 : idx+len(word)]` 的切片范围**逐元素相同**；
- 原代码扫的是 `text_str = folded.folded`（`281`），新函数也必须用 `folded.folded` 构建，不能用 `folded.text` 或原始文本；
- 原代码的 `while idx != -1 and idx < cut_pos` 会提前退出，但它只在 `idx >= cut_pos` 时退出，而那些位置对当前切点不可能满足 `idx < cut_pos`，所以提前退出不改变结果；
- `positions` 可能跳过某些字符（未对齐字/零宽字符），但原实现扫的也是整段 `text_str` 而非 `positions`，所以用整段建表**语义一致**。

**注意一个容易被顺手改掉的隐含语义**：`310-311` 的 `if next_pos > prev_pos + 1: continue` 表示"只在相邻（连续）字符之间判断禁切"。重构时不要把这层判断去掉——它是"零宽字符/未对齐字之间不判禁则"的保证，去掉会让大量正常切点被误判为禁切。

**诚实的收益修正**：段内 `n` 通常 ≤ 130（16s × 8 字/秒），每次 `find` 都是 C 层扫描，单段**估算**约 0.1–0.5ms（未实测）；2000 段合计 0.2–1s，占端到端 <1%。**原文档"段多时可见"是乐观了——这条不该被当作性能项排期。** 它的真实价值是：把平方项消掉，让这段代码在长段（关闭 VAD 整段送模、或 16s 满窗长句）时不会退化成平方级；同时它是 A5-b 抽公共禁则函数的前置步骤，顺手就做了。

**成本**：约 15 行。**风险**：极低。**验证**：对拍——随机取 1 万条日文文本（含禁切词、长音符、片假名连写），新旧实现对每个切点输出 `costs` 数组，要求**完全相等**；不等即视为重构失败。

**不建议做的性能项**：
- 给 Silero VAD 上 GPU——CPU 上已足够快，搬上 GPU 的传输开销大于收益。
- 把 `forced_align` 挪到 GPU——`log_probs` 需要转 CPU，段内 T 只有几百帧，GPU kernel 启动开销更大（`qwen_ctc.py:648` 现在就是 CPU，是对的）。
- 多进程并行转写——模型权重 4GB，进程间不共享，内存直接翻倍。

## 6. 怎么证明优化真的有效（先建度量，再改代码）

## 7. 不要动（Negative List）

这七条都是"看起来能优化、实际不该碰"的：

1. **不要换 VAD**。Silero 是当前"精度 / 体积 / CPU 可跑"的最优解；pyannote 需要额外权重与 GPU，与"全本地、轻量"的定位直接冲突。
2. **不要试图提高 CTC 时间分辨率**。40ms = encoder 80ms ÷ upsample 2，是 head 训练时定死的；改 head 需要重训，不是代码问题。
3. **不要为"更好看"重写前端波形与状态机**。DPR 适配、rAF 播放线、`fastSeek` 松手才跳、撤销栈、断点续跑都已到位；重写只会引入回归。
4. **不要在没有标注集的情况下改默认参数**。VAD 阈值、`cue_pad`、`max_chars` 都是用户可调项，改默认会破坏 6 套历史预设的语义。要改就加档位、加标注，不改默认。
5. **不要引入第二个 ASR 模型做"二次投票"**。成本翻倍、收益不确定，且直接违背"模型固定"的前提。
6. **不要默认打开 `dynaudnorm`**。Whisper 路径默认关是经过考虑的；B4 是加档位，不是改默认。
7. **不要为了性能牺牲可取消性与增量保存**。这是本项目相对 CLI 工具的核心差异；任何批处理/并行改造都必须保留 `cancel_event` 在每个段边界可中断。

## 9. 一句话总结

这个项目的地基不在模型，而在**"分段决定模型听到什么、断句决定字幕怎么出现"**这两层——它们已经做得比大多数同类工具扎实（尤其是 CTC 对齐 + 日语断句 DP 这套组合）。

第一版列出的四条系统性修复（A1 切点、A3 漏句可见、A5 可读性约束、A6 降级可观测）**已全部落地**，共同点是"不改模型、不改默认、低风险"；A4（幻觉闸门）经实测排除。工程侧 P1/P4/P6/P7 也已完成。

**这一批真正的收获不是"改了几处代码"，而是三次"原方案想错了"的当场纠正：**

1. **A5 的 cps 罚分方向是反的**——按每条累加会让目标函数奖励合并，与初衷相反，靠 `CPS_EXCESS_CAP` 封顶才修正；
2. **A6 的插值判据是错的**——"零宽 = 插值"会把正常对齐误报成降级，正确做法是先记 `aligned_count` 再算差值；而且三桶不守恒（漏了"空结果段"），必须是四桶；
3. **P4 的"撞上限 = 截断"是错的**——复读段同样吃满上限，无条件重跑只是白烧一次前向；按"字/token 密度"区分后才对。

三次都只有一种发现方式：**落地之后拿真实片源跑一遍**。这也是下一阶段最该补的东西——**bench 标注集**。没有它，"效果更好"永远只是主张，不是结论。
