# 中文引擎标定记录（中文_test_1.mp4 / 2026-11-14）

素材：`中文_test_1.mp4`（345s，4K，科技口播，主题是国行 eSIM 办卡与运营商踢皮球；
带持续底噪/BGM，Silero VAD 几乎判不出停顿）。作者把字幕**烧在画面里**，没有字幕文件。

参照：`tune/zh/out/中文_test_1_ref.srt`（188 条 / 2030 字，由画面 OCR 生成后再人工
逐帧核对；作者字幕本身平均 10.8 字/条，中位 10 字、p90 15 字）。参考字幕**不随仓库**。

目标是「一次转写尽量逼近作者字幕」，不是替代人工。复现工具都在仓库外 `tune/zh/`：

```bash
python tune/zh/run_engine.py --engine sensevoice --media 中文_test_1.mp4 \
    --out tune/zh/out/sv.srt                    # 产品默认参数跑一次（含耗时）
python tune/zh/sweep.py  --engine sensevoice --media 中文_test_1.mp4 \
    --ref tune/zh/out/中文_test_1_ref.srt --grid "max_segment_s=8|10|12"   # 网格扫参
python tune/zh/replay.py --engine firered --media 中文_test_1.mp4 \
    --capture tune/zh/out/fr_segments.json      # 缓存每段识别结果（FireRed 解码很贵）
python tune/zh/replay.py --engine firered --cache tune/zh/out/fr_segments.json \
    --audio /tmp/zh_audio_16k.wav --ref tune/zh/out/中文_test_1_ref.srt \
    --grid "max_cue_chars=12|14|16"             # 只重跑断句，不加载模型
python tune/zh/cue_stats.py --reference ... --hypothesis ...   # 边界一致率 P/R/F1
python tune/zh/cut_quality.py x.srt             # 切点落在词里的比例（jieba 判定）
```

参考字幕的生成链路：`tune/zh/build_ref.py`（10fps 裁字幕条 → 白字阈值化 → macOS Vision
OCR → 同文本合并）→ `tune/zh/clean_ref.py`（人工逐帧核对的 17 处覆盖 + OCR 抖动去重）。
**不要直接拿 OCR 原样当参照**：作者画面的背景里还有手机截图、短信大字，不阈值化就会把
「2月写…」「8分鐘」读进字幕。

## 0. 结论：默认参数与四处结构性修复

| 参数 | 旧默认 | 新默认 | 依据 |
| --- | --- | --- | --- |
| `sensevoice.max_segment_s` | 16 | **10** | 8–16s 的 CER 在 0.5pt 噪声内（6.35–6.80%），10s 在「文本稳定」与「段边界吃字」之间折中；更长的窗口没有收益 |
| `sensevoice.max_cue_chars` | 18 | **14** | 14 字与作者字幕的 p90 对齐；配合词边界后条均 9.8 字（作者 10.8） |
| `firered.max_segment_s` | 14 | **20** | 该模型没有时间戳，段边界就是时间轴边界；窗口太短会切在词里（32.6s 处「实体 / 的SIM卡」被切成「…实体。 / T的 SIM卡」）。10/14/20/25s 的 CER = 6.45 / 6.31 / **5.91** / 6.01% |
| `firered.max_cue_chars` | 18 | **14** | 同 SenseVoice；旧默认会把两句并成一条 15–16 字字幕 |
| `firered.energy_align` | （无此参数） | **开** | 无时间戳引擎按整段均分时，切点跨着停顿走；改为按能量铺在「有声区间」上，同一组参数下边界 F1 0.511 → 0.543、块准确率 17.3% → 21.1% |

四处结构性修复（都在 `core/`）：

1. **sherpa 的时间戳是「片段内相对秒数」，旧代码当成了绝对时间轴**（`core/text_cues_zh.build_timed_chars`）。
   全部字符被 clamp 到段起点 → 整段字幕塌成 0.3 秒 → 后面的条因为重叠被 `_dedupe`
   丢掉。**SenseVoice 默认参数 CER 69.41% 的根因就是这一条**，修复后 6.55%。
2. **`_extend_to_marks()` 把 `start` 加了两次**（`start + limit + extra`）。窗口被放大到
   20+ 字，实测把一条字幕拉到 **39 字 / 5.8 秒**，同时越过 `max_cue_chars` 与
   `max_cue_dur` 两条上限。这是 FireRed「断句别扭」里最显眼的一条。
3. **空格被当成弱切点**：FireRed 把 eSIM 拆成 `E`/`SIM` 两个 token（文本里也带空格），
   旧规则会切出「国内的 E / SIM了」；SenseVoice 侧则有「E s im」这种按 ASCII 相邻补空格
   的重建错误。现在空格不算切点，且「单字母 + 英文词」之间禁止切。
4. **中文没有词边界**：只按字数硬切会切出「办 / 理」「手 / 机」。`core/text_cues_zh`
   现在用 jieba 的词边界（`word_starts()`）兜底：句末标点 → 停顿 → 逗号 → 词首 →
   最后才按字数硬切；停顿落在词中间时**不让切**。没有 jieba 时退化为旧口径。
   另外加了「虚词不当行首、副词不当行尾」的规则（`NO_LINE_START` / `NO_LINE_END`），
   把「…碰国内的 / 的eSIM了」「今天应该 / 是保修期」这类切法挡在源头。

另外补了 **FireRed 的能量对齐**（`voiced_spans()` / `spread_text_voiced()`）：20ms 帧
算 RMS，按 p95 的 12% 判「有声」，把字铺在有声区间上并把停顿留在字与字之间。没有它时
FireRed 的字幕条会跨着静音走，而且切点检测会把停顿摊进某一个字的时长里——正好切在
停顿后那个字的**后面**（「办 / 理」）。

- **边界 F1**：参考字幕的起点有多少在 ±0.4s 内有对应切点（precision/recall 都算）。
  作者是按语义切的、我们是按标点/停顿/词切，不可能全对；0.55–0.66 是这条片子的现实上限。

## 2. 为什么再往下调没有收益

- **SenseVoice 的剩余错误主要是专名**：`eSIM` → `一信 / Esim / Esyim / Eym`、`保修期` →
  `保质期`、`闲鱼` → `咸鱼`。这类错误换窗口长度、VAD 阈值、语言参数都不动（auto 与 zh
  的 CER 是 6.55% vs 6.70%），要的是热词表/术语后处理。
- **FireRed 的剩余错误是 ITN 与拆分**：它没有逆文本归一化，`10月3号` 会写成
  `十月三号`；`eSIM` 会被写成 `E SIM`。前者需要 WeTextProcessing 级别的数字规则，后者
  需要术语表。两者都不是「调参数」能解决的。
- **VAD 参数在这支片子上几乎无感**：素材有持续底噪/BGM，Silero 在 200ms 静音门槛下
  只切出 10 个 stamp（平均 34s），真正切段靠 `max_segment_s` 的强制切分。阈值 0.20/0.25/
  0.30/0.35/0.40 的 CER 是 6.40/6.60/6.55/6.75/6.95%，`merge_gap_s` 0.15–0.90 完全不变。
  所以不要为了「断句」去拧 VAD 阈值——那是日语耳语片才有的收益。
- **`max_cue_dur` 在中文上是死参数**：14 字的上限已经把时长压在 2.5–3.3s，4.3s 的时长
  上限永远轮不到（`max_cue_dur` 只在极慢语速下才起作用）。保留它是为了兼容旧预设。

## 3. 刻意没做的

- **不换模型**：中文路线是「轻量通稿（SenseVoice）+ 精修（FireRed）」两个可选件，
  本次只做两者的一次性标定；换更大的模型不是当前瓶颈。
- **不做语义断句**：中文没有日语助词那种稳定线索，jieba 词边界是这条线上最便宜、
  最稳的提升。更远的方案是「用 SenseVoice 的逐字时间给 FireRed 文本做跨引擎对齐」，
  收益是时间轴更贴发声，但要同时常驻两个引擎，记为后续候选。
- **不内置术语表**：`eSIM`/`iPhone` 这类写法属于素材领域，产品级方案是用户可编辑的
  热词表（日语侧 P1-3 同一件事），不在引擎里硬编码。

## 4. 回归要点（下次改中文分句前）

1. `pytest -q tests/test_text_cues_zh.py tests/test_engines_zh.py`；
2. 用同一支片跑 `tune/zh/run_engine.py` 两次（两个引擎），与本文第 1 节的数字比；
   CER 变化超过 0.5pt 才算变化（单次跑的噪声就在这个量级）；
3. 任何断句改动都要同时看 **CER**、**边界 F1**、**词内切点** 三个数——只看其中一个
   必然会把「条数变多」当成「断句变好」。
